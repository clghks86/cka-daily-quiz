1진단 순서 — 어느 계층이 죽었나▾

트러블슈팅 문제는 증상으로 계층을 좁히는 것이 절반입니다. kubectl 자체가 안 되면 API 계층(apiserver·etcd), kubectl은 되는데 파드가 안 뜨면 스케줄러·컨트롤러·kubelet, 노드가 NotReady면 kubelet·컨테이너 런타임입니다.

증상의심1차 확인
6443 연결 거부 / timeoutkube-apiserver, etcdcrictl ps -a, ss -ltnp | grep 6443
kubectl은 되는데 Pod가 Pendingkube-schedulerkubectl -n kube-system get pods, 이벤트
Deployment를 만들어도 파드가 없음kube-controller-managerkube-system 파드, 컨트롤러 로그
노드 NotReady / 정적 파드 사라짐kubeletsystemctl status kubelet, journalctl -u kubelet -xe
핵심 — 컨트롤 플레인 컴포넌트는 모두 kubelet이 띄우는 정적 파드입니다. 그래서 apiserver가 죽어도 kubectl 대신 crictl·매니페스트 편집으로 고칠 수 있고, 반대로 kubelet이 죽으면 apiserver·scheduler까지 전부 사라진 것처럼 보입니다. 파드가 안 보이면 먼저 kubelet을 의심하세요.

API가 죽었을 때도 되는 명령

sudo crictl ps -a                 # 정적 파드 컨테이너 상태(Exited 포함)
sudo crictl logs <컨테이너ID>      # 컨테이너 로그 (kubectl logs 대체)
sudo ls /etc/kubernetes/manifests/
sudo ss -ltnp | grep 6443
sudo tail -n 50 /var/log/pods/kube-system_kube-apiserver-*/<uid>/*.log
2kubelet — 설정 파일·로그·인증서▾

kubelet은 정적 파드가 아니라 systemd 서비스(kubelet.service)입니다. kubeadm 클러스터에서 손댈 곳은 세 군데입니다.

경로내용
/var/lib/kubelet/config.yamlKubeletConfiguration — staticPodPath, authentication.x509.clientCAFile, cgroupDriver, clusterDNS
/var/lib/kubelet/kubeadm-flags.env--container-runtime-endpoint 등 kubeadm 인자
/etc/default/kubelet (Debian) / /etc/sysconfig/kubelet (RHEL)KUBELET_EXTRA_ARGS
sudo systemctl status kubelet
sudo journalctl -u kubelet -xe --no-pager | tail -n 50
sudo systemctl daemon-reload && sudo systemctl restart kubelet
sudo cat /var/lib/kubelet/config.yaml
kubectl get nodes                       # kubelet이 살아야 Ready 갱신

kubelet이 안 뜨는 대표 원인

  • swap 켜짐 — running with swap on is not supported → sudo swapoff -a + /etc/fstab 주석
  • cgroupDriver 불일치 — kubelet cgroup driver: "systemd" is different from docker cgroup driver: "cgroupfs" → config.yaml의 cgroupDriver를 런타임과 맞춤 (containerd는 SystemdCgroup = true)
  • clientCAFile 경로 오류 — x509: certificate signed by unknown authority 로 apiserver 연결 실패 → 경로를 /etc/kubernetes/pki/ca.crt로 바로잡기
  • 인증서 만료 — kubeadm certs check-expiration → kubeadm certs renew all 후 kubelet 재시작
  • staticPodPath 오류 — 경로가 틀리면 kubelet은 정상인데 컨트롤 플레인 파드가 하나도 안 뜬다
시험 포인트 — config.yaml을 고친 뒤에는 systemctl daemon-reload 다음 restart kubelet. 그리고 kubelet이 죽으면 그 노드의 apiserver·scheduler·controller-manager도 함께 사라집니다(정적 파드라서). 노드가 NotReady면 노드의 kubelet부터.
3kube-apiserver — 6443·인증서·etcd 연결▾

apiserver는 /etc/kubernetes/manifests/kube-apiserver.yaml 의 command 인자로 설정합니다. 파드가 계속 재시작하거나 아예 안 뜨면 이 파일의 인자 오타가 1순위입니다.

sudo cat /etc/kubernetes/manifests/kube-apiserver.yaml
# 확인할 인자
#   --etcd-servers=https://127.0.0.1:2379
#   --secure-port=6443
#   --client-ca-file / --tls-cert-file / --tls-private-key-file
#   --kubelet-client-certificate / --kubelet-client-key
sudo crictl ps -a | grep -E 'kube-apiserver|etcd'
sudo crictl logs <컨테이너ID>
sudo ss -ltnp | grep 6443
sudo kubeadm certs check-expiration

로그에 자주 뜨는 메시지

메시지원인
connection refused ... 127.0.0.1:2379etcd가 죽었거나 --etcd-servers 포트 오타
unable to load client CA file--client-ca-file 경로 오류
x509: certificate has expired인증서 만료 → kubeadm certs renew all
파드가 Error/Exited 반복매니페스트의 잘못된 플래그·이미지 태그

apiserver가 내려가도 이미 떠 있는 워크로드는 계속 돌아갑니다(kubelet이 관리). 다만 kubectl, 새 파드 생성, 상태 갱신은 모두 멈춥니다.

매니페스트 고치는 요령 — kubelet이 디렉터리를 감시하므로 저장하면 몇 초 뒤 자동으로 파드를 다시 만듭니다. 다시 안 뜨면 매니페스트를 /tmp로 옮겨 파드를 내리고, 오류를 고친 뒤 되돌리세요.
4scheduler · controller-manager — 증상으로 구분하기▾

둘 다 정적 파드이고, 죽어도 kubectl은 정상입니다. 무엇이 멈추는지로 구분합니다.

kube-schedulerkube-controller-manager
멈추면새 파드가 Pending에 머묾 (nodeName 미할당)Deployment→ReplicaSet 생성, ReplicaSet→Pod 생성, 노드 상태 감시, Endpoint 생성이 멈춤
계속 되는 것기존 파드·kubectl 정상기존 파드 실행, kubectl 정상
확인kubectl describe pod 이벤트에 FailedScheduling 없음kubectl get rs 가 안 늘어남, 노드가 죽어도 NotReady로 안 바뀜
kubectl -n kube-system get pods -o wide | grep -E 'scheduler|controller-manager'
kubectl describe pod mypod | tail -n 20
kubectl -n kube-system logs kube-scheduler-controlplane     # apiserver 살아있을 때만
sudo crictl ps -a | grep -E 'scheduler|controller-manager'
구분 요령 — FailedScheduling 이벤트가 있으면 스케줄러는 살아 있고 자원·taint·affinity 문제입니다. 이벤트가 아예 없는데 Pending이면 스케줄러 자체를 의심합니다.
5진단 치트시트 & 시험 함정▾

컴포넌트 상태 한 번에 보기

# 예전 방식 (1.19+ deprecated, <unknown> 이 뜰 수 있음)
kubectl get componentstatuses
kubectl get cs

# 지금 쓰는 방식 — apiserver 자체 헬스 체크
kubectl get --raw='/readyz?verbose'
kubectl get --raw='/livez?verbose'

# apiserver 엔드포인트가 Service에 등록됐는지
kubectl get endpoints kubernetes
kubectl get endpointslices -n default

kubectl cluster-info
kubectl -n kube-system get pods -o wide
kubectl get nodes -o wide
sudo crictl ps -a
sudo journalctl -u kubelet -xe

시험 함정 체크리스트

  • 정적 파드는 매니페스트 파일로만 고친다 — kubectl edit/delete 불가
  • apiserver가 죽으면 kubectl logs·kubectl exec도 안 된다 → crictl logs
  • systemctl restart kube-apiserver 같은 유닛은 없다 (kubelet만 systemd 서비스)
  • kubelet 수정 후 daemon-reload → restart, 그리고 kubectl get nodes로 Ready 확인
  • kube-system 파드 이름 뒤에는 노드 이름이 붙는다 — kube-apiserver-controlplane
  • componentstatuses는 deprecated — 헬스는 /readyz?verbose 또는 Service 엔드포인트로
  • 고친 뒤에는 원래 상태로 되돌리기(백업해 둔 매니페스트 복원, systemctl start)까지가 문제
