1Probe 3종 — startup / readiness / liveness 의 역할과 순서▾

Probe 는 컨테이너가 아니라 노드의 kubelet 이 실행합니다. 파드 IP 로 요청을 보내 결과만 보고 판단하고, 세 종류는 실패했을 때 벌어지는 일이 완전히 다릅니다. 시험도 실무도 이 차이 하나로 갈립니다.

Probe실패하면성공하면 / 기동 중
startupProbe컨테이너를 죽이고 재시작(예산 소진 시 CrashLoopBackOff)성공 전까지 liveness·readiness 는 아예 실행되지 않는다
readinessProbePod Ready=False → EndpointSlice 에서 빠져 트래픽만 끊김. 재시작 없음다시 Ready 가 되면 자동으로 엔드포인트에 복귀
livenessProbekubelet 이 컨테이너를 종료 후 재시작 → 반복되면 CrashLoopBackOff아무 일도 없음(정상 신호). 재시작 카운터 초기화

순서가 핵심입니다. startupProbe 가 있으면 그 성공 전까지 liveness 와 readiness 는 돌지 않습니다. 그래서 “기동이 3분 걸리는 앱”의 정답은 liveness 의 initialDelaySeconds 를 180 으로 늘리는 것이 아니라 startupProbe 를 따로 두는 것입니다 — 기동 후에는 짧은 주기로 계속 감시할 수 있기 때문입니다.

필드 기본값 (시험에 그대로 나온다)

필드기본값 · 규칙
periodSeconds10 — 검사 주기
timeoutSeconds1 — 응답 대기. 앱이 느리면 여기서 먼저 깨진다
failureThreshold3 — 이 횟수만큼 연속 실패해야 실패로 판정
successThreshold1 — liveness·startup 은 1 만 허용(API 검증). readiness 만 2 이상 가능
initialDelaySeconds0 — 첫 검사까지 대기. startupProbe 가 있으면 사실상 불필요
startup 예산 = initialDelaySeconds + periodSeconds × failureThreshold. 예) 10초 주기 · 18회 → 최대 180초까지 기다린 뒤에야 포기합니다.

핸들러 4종

  • httpGet — 200~399 면 성공. scheme: HTTPS, httpHeaders, 포트 이름 지정 가능
  • tcpSocket — 포트가 열리면 성공(앱 응답은 보지 않음). DB·캐시처럼 HTTP 가 아닌 것에
  • exec — 명령의 종료 코드 0 이면 성공. 스크립트가 파드 안에 있어야 함
  • grpc — grpc: {port: 5000, service: ""}. gRPC 상태 프로토콜을 kubelet 이 직접(별도 바이너리 불필요)
# 기동이 느린 앱의 정석: startup 으로 기동 구간을 따로 떼어 낸다
spec:
  containers:
  - name: web
    image: registry.example.com/web:2.4.1
    ports: [{ containerPort: 8080, name: http }]
    startupProbe:                       # 성공 전까지 아래 두 개는 쉰다
      httpGet: { path: /healthz, port: http }
      periodSeconds: 10
      failureThreshold: 18              # 최대 180초 기다린다
      timeoutSeconds: 3
    livenessProbe:                      # 기동 후 "죽었나"만 본다
      httpGet: { path: /healthz, port: http }
      periodSeconds: 10
      failureThreshold: 3               # 30초 넘게 응답 없으면 재시작
    readinessProbe:                     # 기동 후 "받을 준비됐나"를 본다
      httpGet: { path: /ready, port: http }
      periodSeconds: 5
      failureThreshold: 2
      successThreshold: 1
# 현재 파드에 어떤 probe 가 붙어 있는지 (describe 의 요약이 가장 빠르다)
kubectl describe pod web-7d9f8b6c5-2xk4p | grep -A4 -E 'Startup|Liveness|Readiness'
#   Liveness:   http-get http://:http/healthz delay=0s timeout=3s period=10s #success=1 #failure=3

kubectl get pod web-7d9f8b6c5-2xk4p \
  -o jsonpath='{.spec.containers[*].livenessProbe.periodSeconds} {.spec.containers[*].livenessProbe.failureThreshold}{"\n"}'

# 왜 죽었는지: 이벤트 + 직전 컨테이너 로그
kubectl get events --field-selector involvedObject.name=web-7d9f8b6c5-2xk4p --sort-by=.lastTimestamp | tail -5
#   Warning  Unhealthy  ...  Liveness probe failed: Get "http://10.244.1.5:8080/healthz": dial tcp ...: connect: connection refused
#   Normal   Killing    ...  Container web failed liveness probe, will be restarted
kubectl logs web-7d9f8b6c5-2xk4p --previous --tail=30

# 앱이 실제로 그 경로·포트에 답하는지 파드 안에서 확인
kubectl exec -it web-7d9f8b6c5-2xk4p -- \
  sh -c 'wget -qO- localhost:8080/healthz || curl -sS -o /dev/null -w "%{http_code}\n" localhost:8080/healthz'

# 종료 코드로 원인 구분: 137=SIGKILL(재시작·OOM), 143=SIGTERM(정상 종료)
kubectl get pod web-7d9f8b6c5-2xk4p -o jsonpath='{range .status.containerStatuses[*]}{.name} restarts={.restartCount} last={.lastState.terminated.exitCode} reason={.lastState.terminated.reason}{"\n"}{end}'

자주 틀리는 조합

  • readiness 경로를 liveness 에도 그대로 — readiness 는 /ready(의존성 포함), liveness 는 /healthz(프로세스 생존)로 나누지 않으면, DB 가 잠깐 느려질 때 멀쩡한 파드가 전부 재시작됩니다.
  • liveness 에 외부 의존성 검사 — 외부 장애가 클러스터 전체 재시작 폭풍이 됩니다. 의존성은 readiness 에.
  • timeoutSeconds: 1 그대로 두고 느린 엔드포인트 — 앱은 정상인데 probe 만 실패합니다.
  • startupProbe 없이 긴 initialDelaySeconds — 배포 때마다 “언제까지 기다릴지”를 사람이 맞춰야 하고, 재시작 후에도 같은 시간을 또 기다립니다.
2PDB (PodDisruptionBudget, policy/v1) — 자발적 중단의 예산▾

PDB 는 “동시에 몇 개까지 내려가도 되는가”를 선언하고, Eviction API 가 그 예산을 확인한 뒤에만 파드를 내립니다. kubectl drain·kubectl eviction·노드 오토스케일러의 축출이 이 경로를 씁니다. 즉 PDB 는 막는 장치가 아니라 허용하는 장치입니다 — 예산이 0 이면 아무것도 못 내린다가 결론입니다.

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: web-pdb, namespace: prod }
spec:
  minAvailable: 2                 # 또는 maxUnavailable: 1 — 둘 동시 지정 불가(API 거부)
  selector:
    matchLabels: { app: web }
  unhealthyPodEvictionPolicy: AlwaysAllow   # 기본 IfHealthyBudget
항목minAvailablemaxUnavailable
의미중단 후에도 남아 있어야 하는 최소 개수동시에 내려가도 되는 최대 개수
예산 계산현재 Healthy − minAvailablemaxUnavailable 그대로
백분율올림 (7개에 50% → 4개 보장)올림 — 실제 중단이 선언값을 넘을 수 있다
쓰는 곳quorum(etcd·ZooKeeper), 단일 인스턴스replica 수가 변하는 무상태 서비스
policy/v1 의 함정 — 빈 selector({})는 네임스페이스의 모든 파드를 고릅니다(v1beta1 과 반대). selector: {} 를 “아무것도 안 고름”으로 생각하고 넣으면 그 namespace 의 drain 이 전부 막힙니다.
# 예산이 0 인지 확인 — ALLOWED DISRUPTIONS 가 핵심 숫자
kubectl get pdb -n prod
# NAME      MIN AVAILABLE   MAX UNAVAILABLE   ALLOWED DISRUPTIONS   AGE
# web-pdb   2               N/A               1                      10m

kubectl describe pdb web-pdb -n prod | sed -n '/Status:/,/Events:/p'
# Status:
#   Current Healthy:    3
#   Desired Healthy:    2
#   Disruptions Allowed: 1
#   Expected Pods:      3

# drain 은 cordon → evict(Eviction API) 순서. --dry-run=server 로 먼저 확인
kubectl drain node-1 --ignore-daemonsets --delete-emptydir-data --dry-run=server
kubectl drain node-1 --ignore-daemonsets --delete-emptydir-data
# error: Cannot evict pod as it would violate the pod's disruption budget.

# Eviction API 를 직접 때려 보기 (429 Too Many Requests = 예산 소진)
cat <<EOF | kubectl create -f -
{"apiVersion":"policy/v1","kind":"Eviction","metadata":{"name":"web-1","namespace":"prod"}}
EOF

kubectl uncordon node-1     # drain 취소 후 되돌리기

PDB 가 막는 것 / 못 막는 것

구분내용
막는다kubectl drain, Eviction API, 노드 오토스케일러의 축출 — 자발적 중단
못 막는다노드 다운·커널 패닉·OOM 같은 비자발적 중단(대신 예산에는 계산된다)
우회된다파드·Deployment 직접 삭제, kubectl drain --disable-eviction(직접 DELETE), 스케줄러의 preemption
적용 안 됨Deployment·StatefulSet 의 롤링 업데이트는 PDB 가 아니라 maxUnavailable/maxSurge 로 제어
  • --force 는 PDB 우회가 아닙니다 — 컨트롤러가 없는(고아) 파드를 지우도록 허용하는 옵션입니다. 예산을 무시하려면 --disable-eviction 이고, 그건 가용성 보장을 스스로 버리는 선택입니다.
  • 예산은 .metadata.ownerReferences 로 의도한 개수(.spec.replicas) 를 찾아 계산합니다. 컨트롤러 없는 파드 묶음은 기대 개수를 알 수 없어 계산이 어긋납니다.
  • unhealthyPodEvictionPolicy: AlwaysAllow 는 예산이 0 이어도 이미 Running 이 아닌 파드는 내리게 해 줍니다 — “망가진 파드가 drain 을 영원히 막는” 상황의 해법입니다.
3PriorityClass & Preemption — 누가 먼저 들어가고 누가 밀려나는가▾

우선순위는 큐의 순서와 축출의 권한 두 가지로 작동합니다. 스케줄러는 Pending 파드를 우선순위 순으로 꺼내고, 자리가 없으면 자기보다 낮은 우선순위 파드를 축출(preempt) 해 자리를 만듭니다.

apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata: { name: web-high }
value: 1000000                # 값이 클수록 높다. 상한 10억(1e9)
globalDefault: false          # true 는 클러스터에 1개만
description: "prod web pods only"
---
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata: { name: batch-low }
value: 100
preemptionPolicy: Never       # 큐에서는 앞서지만, 남을 축출하지는 않는다
규칙내용
값 범위−2,147,483,648 ~ 1,000,000,000. 그보다 큰 값은 system-node-critical(2,000,001,000)·system-cluster-critical(2,000,000,000) 등 시스템 전용
이름 제약DNS subdomain, system- 접두사 금지
파드 연결priorityClassName → admission 이 .spec.priority 를 채운다. 없는 이름이면 파드 생성이 거부된다
globalDefault파드에 priorityClassName 이 없을 때 쓰는 값. 1개만 가능, 기존 파드에는 소급되지 않음
preemptionPolicy기본 PreemptLowerPriority. Never 면 축출하지 않고 기다린다(자원이 자연히 비면 그때 먼저 배치). 단 자신은 더 높은 우선순위에 축출될 수 있다
kubectl get priorityclass
# NAME                      VALUE        GLOBAL-DEFAULT   AGE
# system-cluster-critical   2000000000   false            32d
# system-node-critical      2000001000   false            32d
# web-high                  1000000      false            3m

kubectl create priorityclass web-high --value=1000000 --description="prod web"
kubectl create priorityclass batch-low --value=100 --preemption-policy=Never

# 파드에 실제로 적용된 값 확인
kubectl get pod web-xxx -o jsonpath='{.spec.priorityClassName} → {.spec.priority}{"\n"}'
# web-high → 1000000

# 축출이 일어났는지: 이벤트 + Pending 파드의 nominatedNodeName
kubectl get events -A --field-selector reason=Preempted
kubectl get pod queued-report -o jsonpath='{.status.nominatedNodeName}{"\n"}'
# worker-2   ← 이 노드의 낮은 우선순위 파드를 쫓아내고 자리를 예약했다
  • 축출된 파드는 즉시 사라지지 않고 종료 유예(terminationGracePeriodSeconds)를 받습니다. 그래서 우선순위 파드도 그동안 Pending 으로 기다립니다.
  • nominatedNodeName 은 예약일 뿐 보장이 아닙니다 — 그 사이 다른 파드가 자리를 차지하면 우선순위 파드는 다시 큐로 갑니다.
  • 낮은 우선순위 파드의 컨트롤러가 다른 노드에 다시 만듭니다 — 우선순위는 “삭제”가 아니라 “다른 곳으로 밀어내기”에 가깝습니다.
  • ResourceQuota 로 requests.cpu 같은 자원별 우선순위 사용을 제한할 수 있습니다 — 악의적 사용자가 최고 우선순위를 독점하는 것을 막는 장치입니다.
  • 우선순위 클래스를 삭제해도 기존 파드는 그대로 동작하고, 같은 이름으로 새 파드만 만들 수 없습니다.
4Job & CronJob (batch/v1) — 완료 조건과 동시 실행 정책▾

Job 의 성공 조건은 completions 개수의 파드가 정상 종료(exit 0) 하는 것입니다. parallelism 은 동시에 몇 개까지 돌릴지를 정합니다. 둘 다 기본 1 이고, completions 를 생략한 채 parallelism 만 주면 작업 큐 패턴이 되어 하나가 성공하면 Job 전체가 끝납니다.

apiVersion: batch/v1
kind: Job
metadata: { name: report }
spec:
  completions: 6                 # 성공해야 하는 파드 수
  parallelism: 2                 # 동시 실행 수
  backoffLimit: 4                # 재시도 횟수(기본 6) — 총 시도 = backoffLimit + 1
  activeDeadlineSeconds: 600     # 이 시간을 넘기면 Job 실패(재시도 무의미)
  ttlSecondsAfterFinished: 3600  # 끝난 Job 을 1시간 뒤 자동 삭제
  template:
    spec:
      restartPolicy: Never       # Job 은 Never 또는 OnFailure 만 허용
      containers:
      - name: r
        image: busybox:1.36
        command: ["sh","-c","echo index=$JOB_COMPLETION_INDEX; sleep 5"]
필드동작
backoffLimit재시도 횟수(기본 6). 실패 파드가 남아 있으면 새 파드를 만들고, 간격은 10s → 20s → 40s … 최대 6분까지 늘어난다
activeDeadlineSecondsJob 전체 수명 상한. 넘기면 실행 중 파드를 종료하고 실패로 표시(backoffLimit 보다 우선)
ttlSecondsAfterFinished완료 후 자동 삭제. 없으면 kubectl delete job 로 직접 정리해야 하고, 남은 Job 이 etcd 를 계속 차지한다
completionModeNonIndexed(기본) / Indexed — Indexed 면 파드마다 JOB_COMPLETION_INDEX 0..N−1
podFailurePolicyexit code 별로 재시도/즉시 실패/Ignore 를 지정(영구 오류에서 재시도 낭비 방지)
apiVersion: batch/v1
kind: CronJob
metadata: { name: report-cron }
spec:
  schedule: "*/5 * * * *"          # 5분마다 (분 시 일 월 요일)
  timeZone: "Asia/Seoul"           # 없으면 kube-controller-manager 의 TZ(보통 UTC)
  concurrencyPolicy: Forbid        # Allow(기본) / Forbid / Replace
  startingDeadlineSeconds: 60      # 이 시간을 넘겨 시작하면 그 회차는 건너뛴다
  suspend: false
  successfulJobsHistoryLimit: 3    # 기본 3
  failedJobsHistoryLimit: 1        # 기본 1
  jobTemplate:
    spec:
      backoffLimit: 2
      template:
        spec:
          restartPolicy: OnFailure
          containers:
          - name: r
            image: busybox:1.36
            command: ["sh","-c","date; sleep 120"]
concurrencyPolicy이전 Job 이 아직 Running 이면쓰는 곳
Allow (기본)그냥 새 Job 을 또 만든다 — 겹쳐서 자원을 먹는다겹쳐도 되는 짧은 작업
Forbid이번 회차를 건너뛴다(Running 이 끝나야 다음)배치·정산처럼 중복 실행이 위험한 작업
Replace실행 중 Job 을 취소하고 새 Job 으로 교체최신 회차만 의미 있는 동기화
# 즉시 1회 실행 (CronJob 을 기다리지 않고 테스트)
kubectl create job report-manual-1 --from=cronjob/report-cron
kubectl logs -l job-name=report-manual-1 --tail=20

# CronJob 일시 정지 / 재개
kubectl patch cronjob report-cron -p '{"spec":{"suspend":true}}'
kubectl patch cronjob report-cron -p '{"spec":{"suspend":false}}'

# 진행 상황
kubectl get cronjob,cronjob/report-cron -o wide
kubectl get jobs -l job-name     # 또는: kubectl get jobs --sort-by=.metadata.creationTimestamp
kubectl get job report -o jsonpath='{.status.succeeded}/{.spec.completions} active={.status.active}{"\n"}'
kubectl get pods -l job-name=report --show-labels

# 실패 원인
kubectl describe job report | sed -n '/Events:/,$p'
kubectl logs -l job-name=report --tail=30 --prefix

kubectl delete job report        # 수동 정리 (ttl 이 없을 때)
  • CronJob 이 놓친 회차: 컨트롤러가 오래 멈춰 있으면 밀린 스케줄을 몰아서 만들려 합니다. startingDeadlineSeconds 가 없으면 100회를 넘게 놓친 시점부터는 아예 시작하지 않고 에러만 남깁니다.
  • Job 이 끝나지 않고 계속 도는 것 같을 때: activeDeadlineSeconds 가 없고 앱이 스스로 끝나지 않으면 영원히 Running 입니다. backoffLimit 은 실패에만 적용됩니다.
  • 파드가 Completed 인데 Job 이 실패: completions 를 채우지 못했거나 activeDeadlineSeconds 를 넘겼는지 describe job 의 Conditions(Failed·reason)로 확인합니다.
  • 스케줄 문법 테스트: schedule: "*/5 * * * *" 는 분 시 일 월 요일 5필드. @daily·@hourly 매크로도 됩니다. 시험에서 시간대를 물으면 timeZone 필드 유무를 봅니다.

시험 함정 체크리스트

  • startupProbe 가 성공하기 전에는 liveness·readiness 가 실행되지 않는다
  • readiness 실패는 재시작이 아니다 — READY 0/1 + RESTARTS 0 이면 readiness, RESTARTS 가 늘면 liveness/startup
  • successThreshold 는 liveness·startup 에서 1 만 허용
  • PDB 는 policy/v1, minAvailable·maxUnavailable 동시 지정 불가, 빈 selector = namespace 전체
  • PDB 는 Eviction API 경로만 제한 — 직접 삭제·--disable-eviction·preemption 은 통과
  • --force 는 PDB 우회가 아니다(고아 파드 삭제용)
  • PriorityClass value ≤ 1e9, globalDefault 는 1개, 기존 파드에 소급 없음
  • preemptionPolicy: Never 는 축출하지 않되 축출될 수는 있다
  • Job backoffLimit 기본 6, restartPolicy 는 Never/OnFailure 만
  • CronJob concurrencyPolicy 기본 Allow, history limit 3/1
