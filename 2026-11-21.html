1Service — ClusterIP·NodePort·EndpointSlice 진단▾

Service는 파드 집합 앞의 가상 IP와 이름입니다. 실제 연결은 kube-proxy(iptables/IPVS·nftables)가 Service IP:port → 파드 IP:targetPort로 넘깁니다. 그래서 연결이 안 될 때 어느 쪽이 끊겼는지를 Endpoints로 가릅니다.

type동작시험 포인트
ClusterIP클러스터 내부 가상 IP (기본값)가장 흔한 기본 Service
NodePort모든 노드의 같은 포트로 노출nodePort는 30000–32767 (지정 생략 시 자동 할당)
LoadBalancer외부 LB + NodePort + ClusterIP클라우드 없으면 EXTERNAL-IP가 <pending>
ExternalNameDNS CNAME만 반환, 프록시 없음type: ExternalName + externalName:
HeadlessclusterIP: None → 파드 IP를 A 레코드로StatefulSet·직접 붙기(예: DB)에서 사용

port와 targetPort

spec:
  selector:
    app: web          # ← 이 라벨과 일치하는 파드가 백엔드
  ports:
  - port: 80          # Service가 노출하는 포트 (클라이언트가 부르는 번호)
    targetPort: 8080  # 파드 컨테이너가 실제로 듣는 포트 (생략 시 port와 같음)
    protocol: TCP

진단 순서 — Endpoints를 먼저 본다

증상의심확인
ClusterIP 연결 refused·timeout, Endpoints <none>selector ↔ 파드 라벨 불일치, 파드 NotReady, 다른 네임스페이스kubectl get endpoints web, kubectl get pods --show-labels
Endpoints는 채워졌는데 연결 실패targetPort 오타, 앱이 127.0.0.1에만 바인딩, NetworkPolicykubectl exec로 파드 IP:포트 직접 호출
NodePort로 안 붙음노드 방화벽, externalTrafficPolicy: Local인데 파드가 다른 노드에 있음kubectl get svc -o wide, ss -ltnp
이름으로는 안 되고 IP로는 됨CoreDNS (3번 항목)dig, kubectl -n kube-system get svc kube-dns
kubectl get svc web -o wide
kubectl describe svc web | grep -A2 -E 'Selector|Endpoints'
kubectl get endpointslices -l kubernetes.io/service-name=web -o wide
kubectl get pods --show-labels
kubectl run nettest --rm -it --restart=Never --image=nicolaka/netshoot \
  -- curl -sS -m3 http://web.default.svc.cluster.local
가르는 기준 — Endpoints가 비었으면 Service 정의(selector) 문제, Endpoints가 있는데 안 되면 파드·포트·정책 문제입니다. EndpointSlice는 엔드포인트 컨트롤러가 만들며, publishNotReadyAddresses: true가 아니면 Ready 파드만 들어갑니다.
2NetworkPolicy — 기본값과 policyTypes 함정▾

NetworkPolicy는 허용 목록(allow-list)만 표현합니다. 정책이 하나도 없는 파드는 모든 트래픽이 허용되고, 정책이 하나라도 파드를 선택하면 그 방향은 기본 거부로 바뀌어 명시한 규칙만 통과합니다. 거부 규칙은 따로 쓸 수 없습니다.

# ① 기본 전면 거부 (deny-all) — 네임스페이스의 모든 파드
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: prod
spec:
  podSelector: {}            # 빈 셀렉터 = 네임스페이스의 모든 파드
  policyTypes: ["Ingress", "Egress"]
  # ingress/egress 규칙 없음 → 양방향 전부 차단

policyTypes가 헷갈리는 지점

작성결과
policyTypes: ["Ingress"] + ingress: []전체 Ingress 차단 (빈 배열 = 규칙 없음)
policyTypes: ["Ingress"] + ingress 필드 없음역시 전체 Ingress 차단
ingress: [{}] (빈 규칙 하나)전체 허용 — 조건 없는 규칙
policyTypes 생략Ingress는 항상 포함, Egress는 egress 규칙이 있을 때만 포함
policyTypes에 Egress + egress: []전체 Egress 차단 → DNS(53)까지 막혀 이름 해석 실패
from: [{}] / namespaceSelector: {}모든 소스 / 모든 네임스페이스 허용

AND와 OR — 리스트 항목 vs 한 항목

# OR : from 의 두 항목 중 하나만 맞으면 허용
  ingress:
  - from:
    - podSelector:
        matchLabels: {role: frontend}        # 같은 네임스페이스의 frontend
    - namespaceSelector:
        matchLabels: {env: prod}             # env=prod 네임스페이스의 모든 파드

# AND : 한 항목 안에 함께 쓰면 둘 다 만족해야 허용
  ingress:
  - from:
    - namespaceSelector:
        matchLabels: {env: prod}
      podSelector:
        matchLabels: {role: frontend}        # env=prod 네임스페이스 中 frontend
  • podSelector만 → 정책과 같은 네임스페이스의 파드
  • namespaceSelector만 → 그 네임스페이스의 모든 파드
  • 네임스페이스에는 kubernetes.io/metadata.name: kube-system 라벨이 자동으로 붙습니다(1.21+) — namespaceSelector에 바로 쓸 수 있습니다.
  • Egress로 DNS를 열 때는 UDP·TCP 53 둘 다 넣습니다.
  egress:
  - to:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: kube-system
    ports:
    - {protocol: UDP, port: 53}
    - {protocol: TCP, port: 53}
시험 함정 — NetworkPolicy는 CNI가 지원해야 실제로 동작합니다(Calico·Cilium·Weave·kube-router O, Flannel 단독 X). 그리고 Egress를 막으면 DNS도 같이 죽어 lookup … i/o timeout으로 나타납니다. "외부 통신만 막았는데 모든 게 안 된다" 싶으면 53 포트부터 확인하세요.
3CoreDNS — 이름 해석 경로와 검증▾

파드의 /etc/resolv.conf는 kubelet이 채웁니다. nameserver는 CoreDNS Service의 ClusterIP이고, 그 Service 이름은 kube-dns, 네임스페이스는 kube-system입니다(구 이름이 그대로 남아 있음).

# 파드 안에서 보이는 resolv.conf
search dev.svc.cluster.local svc.cluster.local cluster.local
nameserver 10.96.0.10          # kube-dns ClusterIP
options ndots:5
dev 네임스페이스의 파드에서해석되는 대상
apidev 네임스페이스의 api 만 (search가 dev.svc.cluster.local을 붙임)
api.prodprod 네임스페이스의 api (두 번째 후보 api.prod.svc.cluster.local)
api.prod.svc.cluster.localFQDN — 항상 명확. 다른 네임스페이스에는 이 형태를 쓴다
kubernetes.defaultAPI Service (검증용 표준 주소)

ndots:5는 점이 5개 미만인 이름을 먼저 search 목록에 붙여 시도하라는 뜻입니다. 그래서 짧은 이름은 자기 네임스페이스에서만 찾습니다.

임시 파드로 검증하기

# dig/nslookup 이 든 이미지로 바로 확인 (netshoot = dig·nslookup·curl 포함)
kubectl run -n dev dnstest --rm -it --restart=Never \
  --image=nicolaka/netshoot -- dig +short api.prod.svc.cluster.local

# busybox 계열은 1.28 태그가 nslookup 동작이 안정적
kubectl run dnstest --rm -it --restart=Never --image=busybox:1.28 \
  -- nslookup kubernetes.default

# CoreDNS 자체 점검
kubectl -n kube-system get pods -l k8s-app=kube-dns -o wide
kubectl -n kube-system logs -l k8s-app=kube-dns --tail=50
kubectl -n kube-system get svc kube-dns          # ClusterIP 확인
kubectl -n kube-system get cm coredns -o yaml    # Corefile: kubernetes / forward . /etc/resolv.conf
증상원인
모든 네임스페이스에서 이름 해석 실패CoreDNS 파드 Down·CrashLoop, kube-dns Service 엔드포인트 없음
특정 네임스페이스에서만 i/o timeout그 네임스페이스의 Egress NetworkPolicy가 53을 막음
짧은 이름만 실패다른 네임스페이스의 서비스를 짧은 이름으로 부름 → FQDN 사용
클러스터 밖 도메인만 실패CoreDNS forward 대상(노드 /etc/resolv.conf) 문제
이름 함정 — CoreDNS의 Service는 kube-dns입니다. coredns.kube-system.svc.cluster.local은 없는 이름입니다. Deployment 이름만 coredns입니다.
4Ingress — ingressClassName · pathType▾

Ingress는 규칙만 담은 리소스이고, 실제 프록시는 Ingress 컨트롤러(ingress-nginx 등)가 합니다. 컨트롤러는 IngressClass로 자기가 처리할 Ingress를 고릅니다.

  • spec.ingressClassName: nginx — 현재 표준. kubectl get ingressclass로 이름 확인
  • 클래스가 없고 기본 클래스(ingressclass.kubernetes.io/is-default-class: "true")도 없으면 컨트롤러가 무시 → ADDRESS가 비고 요청은 기본 백엔드 404
  • annotation kubernetes.io/ingress.class은 레거시(deprecated) — 시험은 필드로 쓰는 게 안전
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: api
  namespace: prod
spec:
  ingressClassName: nginx
  tls:
  - hosts: ["api.example.com"]
    secretName: api-tls
  rules:
  - host: api.example.com
    http:
      paths:
      - path: /api
        pathType: Prefix
        backend:
          service:
            name: api-svc
            port:
              number: 80          # 포트 이름(port.name)으로도 지정 가능

pathType — 매칭 규칙

pathType/api/api//api/users/apiv2
ExactOXXX
PrefixOOOX
ImplementationSpecific컨트롤러 구현에 따름

Prefix는 경로 요소 단위로 비교하므로 /api가 /apiv2를 잡지 않습니다. pathType은 필수 필드입니다.

404인가 503인가

응답의미
404 (컨트롤러 기본 백엔드)host·path가 어떤 규칙에도 안 걸림 / 클래스 미지정으로 Ingress가 무시됨
503 Service Temporarily Unavailable규칙은 걸렸는데 백엔드 엔드포인트가 없음(Service 이름·포트 오타, Ready 파드 없음)
kubectl get ingressclass
kubectl describe ingress api -n prod
kubectl get endpoints api-svc -n prod
kubectl -n ingress-nginx get pods
kubectl -n ingress-nginx logs deploy/ingress-nginx-controller --tail=50
순서 — ADDRESS가 비어 있으면 클래스/컨트롤러, ADDRESS는 있는데 404면 host·path, 503이면 백엔드 Service·엔드포인트를 봅니다.
5Gateway API — GatewayClass / Gateway / HTTPRoute▾

Gateway API는 Ingress를 잇는 표준입니다. 리소스가 역할별로 쪼개져 있어 "누가 무엇을 소유하는가"가 분명합니다.

리소스범위역할Ingress 대응
GatewayClass클러스터컨트롤러 구현 선언 — spec.controllerNameIngressClass
Gateway네임스페이스리스너(port·protocol·hostname·TLS) — 실제 LB 진입점, gatewayClassName 참조컨트롤러의 Service/LB
HTTPRoute네임스페이스parentRefs로 Gateway에 붙고 rules.matches·backendRefs로 라우팅Ingress의 rules
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: web-gw
  namespace: prod
spec:
  gatewayClassName: nginx            # GatewayClass 이름
  listeners:
  - name: http
    port: 80
    protocol: HTTP
    hostname: "api.example.com"
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: api-route
  namespace: prod
spec:
  parentRefs:
  - name: web-gw                     # 어느 Gateway에 붙는지
  hostnames: ["api.example.com"]
  rules:
  - matches:
    - path:
        type: PathPrefix             # Exact | PathPrefix | RegularExpression
        value: /api
    backendRefs:
    - name: api-svc
      port: 80
  • CRD가 먼저 있어야 합니다 — kubectl get crd | grep gateway
  • 상태 확인: kubectl get gatewayclass → Accepted, kubectl get gateway → Programmed, kubectl get httproute → Accepted / ResolvedRefs
  • AllowedRoutes 설정 때문에 다른 네임스페이스의 HTTPRoute가 거부될 수 있습니다.
  • HTTPRoute 외에 GRPCRoute·TLSRoute·TCPRoute가 있습니다.

시험 함정 체크리스트

  • NetworkPolicy의 ingress: []는 전부 차단, ingress: [{}]는 전부 허용
  • Egress를 열면 DNS(53/UDP·TCP)를 잊지 말 것 — 안 열면 이름 해석부터 실패
  • podSelector+namespaceSelector를 한 항목에 쓰면 AND, 두 항목이면 OR
  • Service가 안 되면 get endpoints 먼저 — 비었으면 selector, 있으면 targetPort·정책
  • Ingress는 ingressClassName이 없으면 조용히 무시된다
  • CoreDNS Service 이름은 kube-dns(kube-system)
  • 다른 네임스페이스는 svc.ns 또는 FQDN으로 부른다
  • 만든 리소스는 지정한 네임스페이스에 있는지 -n으로 확인
