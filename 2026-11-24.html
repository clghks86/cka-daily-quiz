1RBAC 4개 오브젝트 — 규칙과 범위를 누가 정하나▾

Role·ClusterRole은 규칙(verbs + resources + apiGroups)의 묶음일 뿐이고, 누구에게 줄지는 RoleBinding·ClusterRoleBinding이 정합니다. 그래서 "ClusterRole을 참조했으니 클러스터 전체 권한"이 아니라, binding의 종류가 범위입니다.

binding ＼ roleRole (ns 스코프)ClusterRole (클러스터 스코프)
RoleBinding그 Role의 규칙을 binding의 ns 안에서만 부여ClusterRole의 규칙을 binding의 ns 안에서만 부여
ClusterRoleBinding불가 — roleRef는 ClusterRole이어야 함클러스터 전체(모든 ns + nodes·pv·ns 같은 클러스터 리소스)

ClusterRole이 필요한 경우는 세 가지입니다. ① 모든 네임스페이스에 같은 규칙을 줄 때, ② nodes·persistentvolumes·namespaces처럼 네임스페이스가 없는 리소스, ③ /healthz 같은 nonResourceURLs(ClusterRole에만 쓸 수 있음). 내장 view·edit·admin도 ClusterRole인데, 이들은 RoleBinding으로 묶어 네임스페이스에만 쓰는 것이 기본 사용법입니다.

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: dev
rules:
- apiGroups: [""]          # core 그룹은 빈 문자열
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
- apiGroups: [""]
  resources: ["configmaps"]
  resourceNames: ["app-config"]   # 이름까지 지정 — get/update 에만 유효
  verbs: ["get", "update"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: dev-read
  namespace: dev            # 주체가 아니라 '권한이 적용될' 네임스페이스
subjects:
- kind: ServiceAccount
  name: app-sa
  namespace: dev            # ServiceAccount 는 반드시 명시 (생략 시 binding 의 ns)
- kind: Group
  name: devs
  apiGroup: rbac.authorization.k8s.io
roleRef:                    # 한 번 만들면 변경 불가
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: view
roleRef는 immutable — 이미 만든 RoleBinding의 roleRef를 바꾸면 roleRef: Invalid value: ...: cannot change roleRef로 거부됩니다(권한 상승 방지). 바꿀 일이 있으면 binding을 지우고 다시 만들어야 합니다.

resourceNames는 list·watch에는 필터로 동작하지 않습니다. 이름을 지정할 수 없는 요청이기 때문입니다. 특정 ConfigMap만 쓰게 하려면 get/update만 주고 list는 빼야 합니다.

2명령형 생성과 kubectl auth can-i 검증▾

시험에서는 YAML을 다 쓰기보다 kubectl create role/clusterrole/rolebinding으로 빠르게 만들고, kubectl auth can-i로 즉시 검증하는 흐름이 빠릅니다.

# 1) 규칙(role/clusterrole)
kubectl create role pod-reader --verb=get,list,watch --resource=pods -n dev
kubectl create clusterrole node-viewer --verb=get,list,watch --resource=nodes
kubectl create clusterrole secret-none --verb="" --resource=secrets     # 권한 없음 규칙

# 2) 부여(binding)
kubectl create rolebinding dev-read --clusterrole=view --serviceaccount=dev:app-sa -n dev
kubectl create rolebinding dev-pods --role=pod-reader --user=jane -n dev
kubectl create rolebinding dev-team --role=pod-reader --group=devs -n dev
kubectl create clusterrolebinding nodes-all --clusterrole=node-viewer --group=system:serviceaccounts:dev

# 3) 확인
kubectl get role,rolebinding -n dev
kubectl describe rolebinding dev-read -n dev
kubectl auth can-i list pods -n dev --as=system:serviceaccount:dev:app-sa
kubectl auth can-i create pods -n prod --as=system:serviceaccount:dev:app-sa
kubectl auth can-i --list -n dev --as=system:serviceaccount:dev:app-sa
kubectl auth can-i get /healthz --as=jane          # nonResourceURL
kubectl auth whoami
주체 표기의미
--user=jane인증서 CN이 jane인 사용자
--as-group=devs인증서 O(organization)에 해당하는 그룹. 여러 번 쓸 수 있음
--as=system:serviceaccount:dev:app-sa네임스페이스 dev의 SA app-sa — 시험 단골
system:serviceaccounts모든 SA
system:serviceaccounts:devdev 네임스페이스의 모든 SA
system:authenticated인증에 성공한 모든 주체(익명 제외)
system:masterskubeadm admin.conf의 그룹 — RBAC을 우회한다

kubectl auth can-i는 그 주체로 실제 인가(authorization) 판단만 합니다. 인증이 실패하는 상태(토큰 없음·만료)는 이 명령으로 보이지 않고 401로 드러납니다. --as는 impersonate 권한이 필요하지만, 클러스터 관리자·admin.conf로는 그대로 동작합니다.

# 파일로 선언한 RBAC 을 현재 상태에 맞추기 (없으면 생성, rules/subjects 는 맞춤)
kubectl auth reconcile -f rbac.yaml --dry-run=server
kubectl auth reconcile -f rbac.yaml
3ServiceAccount — 토큰은 투영, 권한은 RBAC▾

ServiceAccount는 파드의 신원이고, RBAC의 주체 이름은 system:serviceaccount:<ns>:<name>입니다. SA는 네임스페이스 스코프라 다른 네임스페이스의 SA를 파드가 쓸 수 없습니다.

항목1.23 이하1.24 이상
토큰 생성SA마다 Secret 자동 생성, 파드에 영구 토큰Secret 자동 생성 없음 — kubelet이 TokenRequest API로 투영
토큰 수명사실상 무기한만료 있음(기본 1h, kubelet이 갱신) · audience 바인딩
마운트 경로/var/run/secrets/kubernetes.io/serviceaccount/같은 경로(projected volume)
kubectl create sa app-sa -n app
kubectl get sa app-sa -n app -o yaml

# 단기 토큰 직접 발급 (기본 1h, 최소 10m) — 디버깅·외부 도구용
kubectl create token app-sa -n app --duration=2h
kubectl create token app-sa -n app --audience=https://api.example.com

# 파드 안에서 토큰을 쓰지 않게 (API 접근이 없는 앱의 기본값)
kubectl patch sa app-sa -n app -p '{"automountServiceAccountToken": false}'
kubectl patch deploy web -p '{"spec":{"template":{"spec":{"automountServiceAccountToken": false}}}}'
  • automountServiceAccountToken은 SA와 Pod 양쪽에 있고, Pod 값이 우선합니다. SA에서 끄고 필요한 파드만 켜는 편이 안전합니다.
  • imagePullSecrets를 SA에 붙이면 그 SA를 쓰는 모든 파드가 자동으로 private 레지스트리를 당길 수 있습니다(Deployment마다 반복하지 않아도 됨).
  • 오래 사는 토큰 Secret이 꼭 필요하면 type: kubernetes.io/service-account-token + annotation kubernetes.io/service-account.name: app-sa로 수동 생성합니다. 토큰 컨트롤러가 채워 줍니다.
401과 403을 구분 — 토큰이 없거나 만료·서명 불일치면 401 Unauthorized(인증 실패), 신원은 확인됐지만 RBAC 규칙이 없으면 403 Forbidden(인가 실패). pods is forbidden: User "system:serviceaccount:app:app-sa" cannot list resource "pods"는 토큰은 정상이고 RoleBinding이 없다는 뜻입니다.
4TLS 인증서 · kubeconfig · CSR 승인▾

쿠버네티스의 사용자 인증은 대부분 x509 클라이언트 인증서입니다. 인증서의 CN이 User, O가 Group이 됩니다 — kubelet은 CN=system:node:<node>, O=system:nodes로 신원을 갖습니다.

경로 (kubeadm)용도
/etc/kubernetes/pki/
ca.crt·ca.key		클러스터 CA (10년). 이것이 만료되면 개별 인증서 renew로 해결되지 않음
apiserver.crtapiserver 서빙 인증서(1년). SAN에 kubernetes·서비스 IP·노드 이름/IP가 들어가야 접속됨
apiserver-kubelet-client.crtapiserver → kubelet 호출용 클라이언트 인증서
front-proxy-ca.crtaggregation layer(metrics-server 등)용
etcd/server.crt · etcd/peer.crtetcd 서빙·피어 인증서
sa.key · sa.pubServiceAccount 토큰 서명 키 — 인증서가 아니라 키 쌍
/etc/kubernetes/admin.conf클러스터 관리자 kubeconfig(system:masters)

새 사용자 인증서 — CSR 승인 흐름

# 1) 키·CSR 생성 (CN=사용자, O=그룹)
openssl genrsa -out jane.key 2048
openssl req -new -key jane.key -subj "/CN=jane/O=devs" -out jane.csr

# 2) CertificateSigningRequest 오브젝트로 제출
kubectl apply -f - <<EOF
apiVersion: certificates.k8s.io/v1
kind: CertificateSigningRequest
metadata:
  name: jane-csr
spec:
  request: $(cat jane.csr | base64 | tr -d '\n')
  signerName: kubernetes.io/kube-apiserver-client
  usages: ["client auth"]
EOF

# 3) 승인 → 서명된 인증서 회수
kubectl get csr
kubectl certificate approve jane-csr     # 거부는 kubectl certificate deny jane-csr
kubectl get csr jane-csr -o jsonpath='{.status.certificate}' | base64 -d > jane.crt

# 4) kubeconfig 조립
kubectl config set-cluster cka --server=https://172.30.1.10:6443 \
  --certificate-authority=/etc/kubernetes/pki/ca.crt --embed-certs=true
kubectl config set-credentials jane --client-certificate=jane.crt \
  --client-key=jane.key --embed-certs=true
kubectl config set-context jane --cluster=cka --user=jane
kubectl --context=jane auth can-i --list

signerName은 kubernetes.io/kube-apiserver-client(사용자 클라이언트 인증서), kubernetes.io/kubelet-serving(kubelet 서빙) 둘 다 수동 승인이 필요합니다. 승인되지 않은 CSR은 Pending에 머물고, 서명은 kube-controller-manager의 csrsigning 컨트롤러가 CA 키로 수행합니다 — CA 키를 직접 만질 필요가 없습니다.

만료 확인과 갱신

kubeadm certs check-expiration
openssl x509 -in /etc/kubernetes/pki/apiserver.crt -noout -subject -issuer -dates

# 만료 임박/만료 시
kubeadm certs renew all
kubeadm certs renew apiserver          # 개별 갱신도 가능

# 컨트롤 플레인 정적 파드는 시작할 때 인증서를 읽는다 → 재시작 필요
mv /etc/kubernetes/manifests/kube-apiserver.yaml /tmp/ && sleep 20
mv /tmp/kube-apiserver.yaml /etc/kubernetes/manifests/

노드 kubelet의 클라이언트 인증서는 kubelet이 CSR API로 스스로 회전합니다(rotateCertificates: true). kubeconfig은 clusters·users·contexts·current-context 구조이고, KUBECONFIG에 여러 파일을 콜론으로 이어 붙이면 병합됩니다(같은 이름은 앞 파일 우선).

증상원인과 조치
401 Unauthorized
You must be logged in		인증 실패 — 토큰 없음·만료, 잘못된 kubeconfig, CA 불일치. kubectl config view --raw, kubectl create token
403 Forbidden
cannot list resource "pods"		인증은 성공, 인가 실패 — RoleBinding 없음·ns 불일치·verb/resource 불일치
분명히 binding 했는데 403binding이 다른 ns에 있음(SA는 app, binding은 default), 또는 subject를 SA가 아닌 User로 넣음
권한을 회수했는데 아직 동작authorizer 캐시로 수 초 지연. system:masters·cluster-admin이 붙어 있지 않은지 먼저 확인
roleRef 변경이 거부됨cannot change roleRef — binding 삭제 후 재생성
CSR이 Pending승인 대기 — kubectl certificate approve <name>. signerName usages 확인
x509: certificate has expired인증 단계 실패 — RBAC 문제가 아님. kubeadm certs renew all + 정적 파드 재시작
error: Unable to connect ... certificate is valid for ...apiserver 서빙 인증서 SAN에 접속 주소가 없음 — 인증서 재발급 또는 접속 주소 변경

시험 함정 체크리스트

  • 권한 범위는 binding이 정한다 — RoleBinding+ClusterRole = 그 ns뿐
  • RoleBinding의 roleRef는 immutable — 지우고 다시
  • SA 주체는 system:serviceaccount:<ns>:<name>, subject에 namespace 명시
  • 토큰은 신원, 권한은 RoleBinding — 401은 토큰, 403은 RBAC
  • 1.24+ 는 SA 토큰 Secret이 자동 생성되지 않는다 — kubectl create token
  • CSR은 approve 후 status.certificate를 base64 디코드해 쓴다
  • 만료는 kubeadm certs check-expiration → renew → 정적 파드 재시작
  • 네임스페이스 없는 리소스(nodes·pv·ns)는 ClusterRole + ClusterRoleBinding
