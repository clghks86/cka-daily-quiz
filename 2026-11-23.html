1PV · PVC · StorageClass — 누가 무엇을 요청하고 누가 만드나▾

PV는 관리자가 준비한 실제 스토리지 조각(용량·accessMode·reclaimPolicy)이고, PVC는 사용자의 요청서(용량·accessMode·storageClassName)입니다. 둘은 1:1로 바인딩되고, 한 번 묶인 PV는 다른 PVC가 다시 쓸 수 없습니다. PV와 StorageClass는 클러스터 스코프(네임스페이스 없음), PVC는 네임스페이스 스코프입니다.

정적 vs 동적 프로비저닝

항목정적 (static)동적 (dynamic)
PV 생성관리자가 YAML로 미리 생성StorageClass의 프로비저너가 자동 생성
PVC가 고르는 것용량·accessMode·class가 맞는 기존 PVstorageClassName으로 SC를 지정
속도맞는 PV가 있으면 즉시 Bound수 초~수십 초, 그동안 Pending
전형NFS·로컬 디스크·기존 볼륨클라우드 CSI (EBS·PD·Azure Disk)
kubectl get pv,pvc,sc                 # pv·sc는 클러스터 스코프, pvc는 현재 ns
kubectl get pvc -A -o wide
kubectl describe pvc data | sed -n '/Events/,$p'
kubectl get pv pv-data -o yaml | grep -A3 -E 'phase|claimRef'
kubectl get pv -o custom-columns=NAME:.metadata.name,CAP:.spec.capacity.storage,MODE:.spec.accessModes[*],SC:.spec.storageClassName,PHASE:.status.phase

정적 프로비저닝에서 가장 흔한 실패는 "PV는 있는데 PVC가 Pending"입니다. PVC의 용량이 PV보다 크거나 accessMode가 다르면 매칭되지 않습니다 — 둘 다 PVC 요청을 만족해야 후보가 됩니다.

2accessModes — 노드 단위(RWO/RWX)와 파드 단위(RWOP)▾
mode무엇을 기준으로 허용하나
ReadWriteOnce
(RWO)		한 노드에서 read-write. 그 노드 위의 여러 파드는 공유 가능
ReadOnlyMany
(ROX)		여러 노드에서 read-only (드라이버가 지원해야 함)
ReadWriteMany
(RWX)		여러 노드에서 read-write. NFS·EFS·CephFS 같은 공유 파일시스템
ReadWriteOncePod
(RWOP)		클러스터 전체에서 파드 하나만. v1.22+ · CSI 지원 필요

accessMode는 "권한 스위치"가 아니라 스토리지가 지원하는 동시 접근 방식입니다. EBS·GCE PD·Azure Disk 같은 블록 볼륨은 RWO만 되고, NFS·EFS는 RWX까지 됩니다. PVC의 accessModes가 PV와 맞지 않으면 바인딩 자체가 되지 않습니다.

Multi-Attach — RWO 볼륨이 이미 한 노드에 붙어 있는데, 그 볼륨을 쓰는 파드가 다른 노드에 스케줄되면 kubelet이 Multi-Attach error for volume ... already used by pod(s) attached to another node로 마운트를 실패시키고 파드는 ContainerCreating에 머뭅니다. replicas > 1 Deployment가 하나의 RWO PVC를 공유할 때 자주 나옵니다. 해결은 RWX 스토리지로 바꾸거나, StatefulSet의 volumeClaimTemplates처럼 레플리카마다 별도 PVC를 주는 것입니다.
3ReclaimPolicy — Retain / Delete 와 Released 상태▾

PVC가 삭제된 뒤 PV(와 백엔드 스토리지)를 어떻게 할지 정합니다. 동적 프로비저닝 PV의 기본은 Delete(SC의 reclaimPolicy로 바꿀 수 있음), 관리자가 만든 정적 PV의 기본은 Retain입니다.

phase의미
Available아직 어떤 PVC에도 묶이지 않음 — 바인딩 후보
BoundPVC와 묶여 사용 중
ReleasedPVC는 지워졌지만 Retain이라 데이터가 남은 상태. 새 PVC와 자동으로 다시 묶이지 않는다
Failed자동 회수·백엔드 해제에 실패

Retain PV는 metadata.claimRef에 예전 PVC가 남아 있어 매칭 대상에서 빠집니다. 데이터를 살리려면 claimRef만 지워 Available로 되돌리고 새 PVC를 만듭니다.

# 데이터 그대로 되살리기 (claimRef 제거 → Available)
kubectl patch pv pv-data --type=json \
  -p '[{"op":"remove","path":"/spec/claimRef"}]'
kubectl get pv pv-data

# 정말 버릴 때 — Retain은 백엔드 스토리지를 직접 지워야 한다
kubectl delete pv pv-data
  • Delete는 PV 오브젝트와 백엔드 볼륨(EBS 등)을 함께 지웁니다.
  • Retain은 PV와 데이터가 남습니다. kubectl delete pv 해도 백엔드 스토리지는 남아 직접 정리해야 합니다.
  • 바인딩된 PV의 reclaimPolicy는 kubectl patch pv ... -p '{"spec":{"persistentVolumeReclaimPolicy":"Retain"}}'로 미리 바꿔 둘 수 있습니다.
4StorageClass — volumeBindingMode · allowVolumeExpansion · default▾
항목ImmediateWaitForFirstConsumer
프로비저닝 시점PVC 생성 즉시파드가 스케줄될 때
PVC 상태곧 Bound소비 파드 전까지 Pending (정상)
강점PVC만 만들고 바로 확인 가능파드의 노드·존 제약에 맞는 볼륨 생성
함정PVC가 먼저 존을 골라 파드가 못 뜸(volume node affinity conflict)파드가 없으면 Pending이 정상 — 고장으로 오해
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast
  annotations:
    storageclass.kubernetes.io/is-default-class: "true"
provisioner: ebs.csi.aws.com
parameters:
  type: gp3
reclaimPolicy: Delete
allowVolumeExpansion: true
volumeBindingMode: WaitForFirstConsumer
kubectl get sc
kubectl get sc fast -o yaml
kubectl get sc -o jsonpath='{range .items[?(@.metadata.annotations.storageclass\.kubernetes\.io/is-default-class=="true")]}{.metadata.name}{"\n"}{end}'
  • storageClassName 생략 = default SC 사용(있을 때). storageClassName: "" = "class 없이 정적 바인딩만" 이라는 명시적 선언이라 default SC를 쓰지 않습니다. 이 한 줄이 Pending 원인의 절반입니다.
  • allowVolumeExpansion: true여야 PVC의 requests.storage를 늘릴 수 있습니다. 줄이는 것은 불가합니다.
  • default SC는 클러스터에 하나만 두는 편이 안전합니다. 확장 후 파드 안 파일시스템 resize가 필요할 수 있습니다(FileSystemResizePending).
# 볼륨 확장 (allowVolumeExpansion: true 인 SC의 PVC만)
kubectl patch pvc data -p \
  '{"spec":{"resources":{"requests":{"storage":"20Gi"}}}}'
kubectl get pvc data -w    # RESIZING → 용량 확인
5PVC Pending · Terminating 트러블슈팅▾ 
# 1) 왜 Pending인가 — describe의 Events가 답
kubectl describe pvc data | sed -n '/Events/,$p'
kubectl get sc
kubectl get events --sort-by=.lastTimestamp | tail -15

# 2) 누가 이 PVC를 쓰고 있나 (Terminating 원인)
kubectl get pods -A -o custom-columns=\
NS:.metadata.namespace,POD:.metadata.name,PVC:.spec.volumes[*].persistentVolumeClaim.claimName
kubectl get pvc data -o yaml | grep -A2 finalizers
메시지 / 상태의미와 조치
no persistent volumes available for this claim and no storage class is setSC를 안 쓰는 PVC인데(생략인데 default 없음 또는 "") 맞는 PV가 없음 → PV 생성 또는 SC 지정
storageclass.storage.k8s.io "xyz" not foundSC 이름 오타 또는 SC 미생성 → kubectl get sc
waiting for first consumer to be created before bindingWaitForFirstConsumer — 소비 파드를 만들면 바인딩. 고장 아님
pod has unbound immediate PersistentVolumeClaims파드가 PVC 바인딩을 기다리며 Pending
Multi-Attach error for volume ...RWO 볼륨을 다른 노드에서 동시 마운트 → RWX로 변경 또는 노드 고정
insufficient capacity / no matching accessMode정적 PV와 요청 크기·mode 불일치

PVC가 Terminating에서 멈출 때 — finalizer kubernetes.io/pvc-protection이 이 PVC를 마운트한 파드가 사라질 때까지 삭제를 막습니다. 파드가 Terminating이면 kubelet의 unmount 완료를 기다리고, 노드가 NotReady면 그보다 더 오래 걸립니다. finalizer를 손으로 지우는 것은 최후 수단입니다 — 볼륨이 붙은 채 PVC만 사라져 데이터가 깨질 수 있습니다.

시험 함정 체크리스트

  • storageClassName 생략 = default SC / "" = 정적만 — Pending 원인의 절반
  • WaitForFirstConsumer에서 PVC Pending은 정상 — 소비 파드를 먼저 확인
  • 재사용 실패는 Released + claimRef — claimRef를 지우면 Available
  • RWO는 노드 단위, RWOP는 파드 단위 — Multi-Attach는 RWX나 노드 고정으로
  • Terminating은 finalizer + 소비 파드 — 마운트 해제 전엔 끝나지 않음
  • 동적 PV 기본 reclaimPolicy는 Delete, 정적 PV는 Retain
  • 확장은 allowVolumeExpansion: true일 때만, 늘리기만 가능
