1Service 4타입 · port 매핑 · Headless DNS▾

Service 는 파드 앞의 가상 IP(VIP)와 규칙의 묶음이고, 실제 트래픽은 각 노드의 kube-proxy 가 만든 DNAT 규칙으로 파드 IP 에 도착합니다. 즉 Service 는 “프록시 프로세스”가 아니라 규칙이고, 그래서 kubectl get svc 에 IP 가 보여도 실제로 연결되는지는 EndpointSlice 와 노드 규칙이 결정합니다.

타입동작과 시험 포인트
ClusterIP
(기본)		클러스터 내부 전용 VIP. DNS svc.ns.svc.cluster.local. 외부에서 안 보임
NodePort모든 노드의 지정 포트(기본 30000–32767)를 연다 + ClusterIP 동시 제공. 파드가 없는 노드로 들어와도 (Cluster 정책이면) 다른 노드 파드로 전달됨
LoadBalancerNodePort + 클라우드 LB 프로비저닝. 실제 IP 는 kubectl get svc -o wide 의 EXTERNAL-IP, 즉 .status.loadBalancer.ingress 에 늦게 채워진다
ExternalNameCNAME 만 반환하는 DNS 별칭. kube-proxy 규칙 없음·selector 없음. DB 호스트처럼 외부 이름을 내부 이름으로 감쌀 때

port · targetPort · nodePort

  • port — 서비스가 노출하는 포트(클라이언트가 부르는 번호). targetPort — 파드 컨테이너의 포트. nodePort — 노드에서 여는 포트.
  • targetPort 는 숫자 또는 컨테이너 포트 이름입니다. 이름으로 지정하면 모든 파드의 컨테이너가 그 이름의 containerPort 를 가져야 하고, 하나라도 없으면 그 파드는 Service 로 트래픽을 못 받습니다.
  • port 만 쓰고 targetPort 를 생략하면 port 와 같은 번호로 전달됩니다 — 앱이 8080 에서 도는데 port: 80 만 적으면 연결이 거절되는 대표 실수입니다.
# 명령으로 만드는 가장 빠른 길 (시험에서 자주 씀)
kubectl expose deploy web --name=web-svc --port=80 --target-port=8080 --type=NodePort
kubectl create service clusterip api --tcp=8080:8080
kubectl create service nodeport api-np --tcp=80:8080 --node-port=31080

# 확인
kubectl get svc,endpoints,endpointslice -o wide
kubectl get svc web -o jsonpath='{.spec.clusterIP} {.spec.ports[*].port} {.spec.ports[*].targetPort}{"\n"}'

Headless Service — VIP 를 없애면 DNS 가 일을 한다

clusterIP: None 이면 kube-proxy 규칙이 없고, DNS 가 Ready 파드 IP 를 A 레코드로 전부 돌려줍니다(클라이언트가 라운드로빈). StatefulSet 처럼 파드별 이름이 필요할 때 씁니다.

# 파드 안에서 확인 (netshoot 등)
dig +short web.default.svc.cluster.local                    # headless → 파드 IP 들
dig +short web-0.web.default.svc.cluster.local              # StatefulSet 개별 파드
dig +short SRV _http._tcp.web.default.svc.cluster.local     # 포트 이름까지
# 0 33 8080 web-0.web.default.svc.cluster.local.

# SRV 가 나오려면 Service port 에 name 이 있어야 한다
ports:
- name: http        # 없으면 SRV 레코드가 만들어지지 않는다
  port: 80
  targetPort: 8080
sessionAffinity 는 쿠키가 아니다 — sessionAffinity: ClientIP 는 클라이언트 IP 기준 고정이며 timeoutSeconds 기본값은 10800초(3시간)입니다. 프록시·NAT 뒤에서 여러 사용자가 같은 IP 로 보이면 한 파드에 몰립니다.
2EndpointSlice — Endpoints 를 대체한 이유와 구조▾

Service 는 파드를 직접 고르지 않습니다. 컨트롤 플레인의 endpointslice controller 가 Service 의 selector 를 평가해 EndpointSlice 를 만들고, 각 노드의 kube-proxy 가 그 slice 를 watch 해 규칙을 갱신합니다. 그래서 연결 문제를 볼 때 Service spec → EndpointSlice → kube-proxy 순서가 됩니다.

항목Endpoints (구)EndpointSlice
APIv1, Service 당 1개discovery.k8s.io/v1 (GA), Service 당 여러 개
주소 상한1,000개에서 잘림slice 당 기본 100개
(--max-endpoints-per-slice)
변경 전파1개가 바뀌어도 전체 재전송바뀐 slice 만 갱신 → watch 부하 분산
부가 정보주소·포트만conditions(ready·serving·terminating), topology(zone·nodeName·hints), addressType(IPv4/6/FQDN)
# Service 별 slice 찾기 — 라벨이 핵심
kubectl get endpointslices -l kubernetes.io/service-name=web -o wide
# NAME          ADDRESSTYPE   PORTS   ENDPOINTS                 AGE
# web-4k2p9      IPv4          8080    10.244.1.5,10.244.1.6     3d

kubectl get endpointslice web-4k2p9 -o yaml | sed -n '1,40p'
# labels:
#   kubernetes.io/service-name: web
#   endpointslice.kubernetes.io/managed-by: endpointslice-controller.k8s.io
# addressType: IPv4
# endpoints:
# - addresses: ["10.244.1.5"]
#   conditions: {ready: true, serving: true, terminating: false}
#   nodeName: worker-1
#   zone: ap-northeast-2a

# 왜 어떤 노드는 ready 인데 트래픽이 안 갈까 → conditions
kubectl get endpointslice -l kubernetes.io/service-name=web \
  -o jsonpath='{range .items[*].endpoints[*]}{.addresses[0]} ready={.conditions.ready}{"\n"}{end}'
  • 구 Endpoints 오브젝트를 조회하면 1,000개까지만 보입니다. “엔드포인트가 1000개에서 끊겼다”는 대규모 클러스터의 정상 동작이고, 해결은 slice 를 보는 것입니다.
  • selector 없는 Service(외부 DB 등)는 controller 가 slice 를 만들지 않으므로 직접 EndpointSlice 를 만들어야 합니다. 이때도 kubernetes.io/service-name 라벨과 addressType 이 없으면 kube-proxy 가 무시합니다.
  • service.kubernetes.io/topology-mode: Auto 를 Service 에 달면 hints(zone)를 이용한 topology-aware routing 으로 같은 zone 파드를 우선 씁니다(가능할 때만).
3kube-proxy — iptables vs IPVS, 그리고 externalTrafficPolicy▾

kube-proxy 는 DaemonSet 으로 모든 노드에서 돌며 Service·EndpointSlice 를 감시해 노드의 패킷 처리 규칙을 다시 씁니다. 모드는 kube-system/kube-proxy ConfigMap 의 mode 와 로그로 확인합니다.

kubectl -n kube-system get cm kube-proxy -o jsonpath='{.data.mode}'; echo
kubectl -n kube-system logs ds/kube-proxy --tail=5
# "Using iptables Proxier." / "Using ipvs Proxier."
kubectl -n kube-system get pod -l k8s-app=kube-proxy -o wide
항목iptablesIPVS
자료구조chain 규칙 (KUBE-SERVICES→KUBE-SVC-…→KUBE-SEP-…)커널 L4 LB 의 hash table
비용규칙 수에 비례(O(n)) — 서비스·엔드포인트가 늘면 조회·동기화(SyncProxyRules)가 느려짐조회 O(1). 수천 서비스에서도 안정적
분산-m statistic --mode random 균등 확률스케줄러 선택: rr, wrr, lc, wlc, sh, dh, sed
전제기본값. 별도 준비 없음ip_vs·ip_vs_rr·nf_conntrack 모듈, ipset. ClusterIP 는 kube-ipvs0 더미 인터페이스에 올라간다
확인iptables-save | grep -c KUBE-SVCipvsadm -Ln, ip addr show kube-ipvs0

최근 릴리스에는 nftables 모드도 있습니다(1.29 알파 → 1.31 베타). iptables 의 규칙 수 문제를 nftables set 으로 해결하는 방향이고, IPVS 처럼 커널 모듈을 따로 요구하지 않습니다. 시험에서는 “규모 때문에 느리다 → IPVS”, “모드 확인은 ConfigMap·로그” 두 가지만 확실하면 됩니다.

# 모드 전환 (노드에 모듈이 없으면 kube-proxy 가 뜨지 못하니 먼저 확인)
kubectl -n kube-system get cm kube-proxy -o yaml > kube-proxy.bak.yaml
kubectl -n kube-system patch cm kube-proxy --type merge -p '{"data":{"mode":"ipvs"}}'
kubectl -n kube-system rollout restart ds/kube-proxy
kubectl -n kube-system rollout status  ds/kube-proxy

# 노드에서
sudo lsmod | grep -E '^ip_vs'
sudo ipvsadm -Ln | head -20
ip addr show kube-ipvs0 | head -5

externalTrafficPolicy — 2-hop 을 없앨 것인가, 클라이언트 IP 를 살릴 것인가

항목Cluster (기본)Local
전달 범위들어온 노드에서 SNAT 후 다른 노드 파드로도 전달(2-hop)그 노드의 파드로만
클라이언트 IP가려짐(노드 IP 로 SNAT)보존 — 앱이 실제 IP 를 본다
파드 없는 노드정상 동작(포워딩)트래픽을 버린다(포워딩 안 함)
LB 헬스체크불필요healthCheckNodePort 로 노드별 Ready 여부를 LB 가 확인해야 함
쓰는 곳일반적인 웹 서비스IP 기반 정책·로깅, 홉 감소가 중요한 LB
  • internalTrafficPolicy 는 같은 개념을 클러스터 내부 트래픽에 적용합니다(Cluster/Local).
  • Local 에서 “특정 노드만 응답 없음”은 버그가 아니라 정책입니다. LB 가 healthCheckNodePort 를 보게 하거나 Cluster 로 바꿉니다.
  • NodePort 는 healthCheckNodePort 를 자동으로 만들지 않습니다(LoadBalancer 만 자동). 그래서 NodePort + Local 조합은 노드별 접근 제어를 직접 해야 합니다.
4Gateway API — GatewayClass · Gateway · HTTPRoute▾

Gateway API 는 Ingress 의 “구현체마다 다른 annotation” 문제를 역할과 표준 필드로 분리한 L7 라우팅 API 입니다. GatewayClass·Gateway·HTTPRoute 는 gateway.networking.k8s.io/v1 로 GA 입니다.

오브젝트누가 · 무엇을
GatewayClass인프라 제공자가 정의 — 어떤 컨트롤러(구현체)가 처리하는지(controllerName)
Gateway클러스터 운영자 — 리스너(포트·프로토콜·호스트·TLS 인증서)와 allowedRoutes. LB IP 는 .status.addresses 에 채워진다
HTTPRoute앱 팀 — parentRefs 로 Gateway 에 붙고, hostnames·rules(matches·filters·backendRefs)를 소유
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata: { name: prod-gw, namespace: infra }
spec:
  gatewayClassName: nginx           # GatewayClass 이름
  listeners:
  - name: http
    port: 80
    protocol: HTTP
    hostname: "api.example.com"
    allowedRoutes:
      namespaces: { from: Selector, selector: { matchLabels: { gw: prod } } }
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: { name: api, namespace: app }
spec:
  parentRefs:
  - { name: prod-gw, namespace: infra }
  hostnames: ["api.example.com"]
  rules:
  - matches:                        # path 가 같으면 헤더 매칭 rule 이 우선
    - headers: [{ name: x-beta, value: "1" }]
    backendRefs: [{ name: api-v2, port: 80 }]
  - matches:
    - path: { type: PathPrefix, value: /v1 }
    backendRefs:
    - { name: api-v1, port: 80, weight: 90 }
    - { name: api-v2, port: 80, weight: 10 }   # 90:10 비율(합 100 강제 아님)

Ingress → HTTPRoute 로 옮길 때

IngressGateway API주의
spec.rules[].host + path(Exact/Prefix)hostnames + matches.path(Exact/PathPrefix/RegularExpression)ImplementationSpecific 은 구현체 동작이라 그대로 못 옮긴다
nginx.ingress.kubernetes.io/canary-weightbackendRefs[].weight표준 필드 — 벤더 무관
canary-by-header / -valuerules[].matches[].headerspath 가 같으면 헤더 매칭이 있는 rule 이 우선
rewrite-targetfilters: URLRewrite정규식 치환은 구현체 지원 여부 확인
ssl-redirectfilters: RequestRedirect(scheme https)리스너 TLS 와 함께 설계
IngressClassGatewayClass + GatewayTLS·LB 설정이 Gateway 로 올라가 한 곳에서 관리된다
  • 필터: RequestHeaderModifier, ResponseHeaderModifier, URLRewrite, RequestRedirect, RequestMirror, ExtensionRef.
  • Route 는 namespace 경계를 넘어 붙을 수 있습니다(parentRefs + Gateway 의 allowedRoutes). 앱 팀이 자기 namespace 에서 라우트만 고치면 되는 구조.
  • Ingress NGINX 프로젝트는 2026년 3월 지원 종료가 예고되어 있어, 기존 Ingress 자산이 있는 조직은 Gateway API 로의 이전을 검토하는 흐름입니다.
  • 상태 확인은 describe 의 status.parents[].conditions — Accepted(Gateway 가 받았나)와 ResolvedRefs(backendRefs 가 실제 Service 를 가리키나)를 봅니다.
kubectl get gatewayclass
kubectl get gateway,httproute -A
kubectl describe httproute api -n app | sed -n '/Status:/,/Events:/p'
kubectl get httproute api -n app \
  -o jsonpath='{range .status.parents[*]}{.parentRef.name} {.conditions[*].type}={.conditions[*].status}{"\n"}{end}'
5연결이 안 될 때 진단 순서 · 시험 함정 체크리스트▾ 
# 0) 파드 안에서 직접 때려 보는 것이 가장 빠르다

시험 함정 체크리스트

  • kubectl get endpoints 의 <none> 은 selector 불일치이거나 파드 미준비 — 두 경우를 endpointslice 의 conditions.ready 로 구분
  • 1,000개 상한은 Endpoints — 대규모는 slice 를 본다
  • externalTrafficPolicy: Local 은 파드 없는 노드에서 버린다(고장 아님)
  • ClusterIP 는 모든 노드에서 유효 — Service 하나 만들면 노드마다 규칙이 생긴다
  • IPVS 전환은 ConfigMap + DaemonSet 재시작, 확인은 ipvsadm -Ln
  • HTTPRoute 가 안 붙으면 status.parents 의 Accepted/ResolvedRefs 를 본다
  • ExternalName 은 kube-proxy 규칙이 없다 — iptables 에서 찾으면 안 된다
  • port-forward 는 kubelet 경유라 Service·NetworkPolicy 를 검증하지 못한다
