1Taint & Toleration — 노드가 거르는 조건▾

방향이 반대입니다. taint는 노드에 붙고(노드가 파드를 밀어냄), toleration은 파드에 붙습니다(파드가 그 taint를 견딤). 둘은 허가일 뿐이라 toleration이 있어도 파드가 그 노드로 간다는 보장은 없습니다 — 그건 nodeSelector/nodeAffinity의 몫입니다.

effect동작
NoScheduletoleration 없는 새 파드를 배치하지 않음. 이미 Running인 파드는 그대로
PreferNoSchedule가능하면 피함. 다른 노드가 없으면 결국 배치(소프트)
NoExecute새 파드 거부 + toleration 없는 기존 파드를 축출. tolerationSeconds로 유예 시간을 줄 수 있음

명령

# 붙이기 / 제거(-) — 제거는 key만 적으면 값·effect 무관하게 지워진다
kubectl taint nodes node1 gpu=true:NoSchedule
kubectl taint nodes node1 gpu=true:NoSchedule-
kubectl taint nodes node1 dedicated-

kubectl get nodes -o custom-columns=NAME:.metadata.name,TAINTS:.spec.taints
kubectl describe node node1 | grep -A3 -i taint

toleration 매칭 규칙

실무 포인트 — 시스템 taint는 노드 컨트롤러가 자동으로 붙입니다: node.kubernetes.io/not-ready·unreachable·memory-pressure·disk-pressure·pid-pressure·unschedulable. kubeadm의 컨트롤 플레인 taint는 node-role.kubernetes.io/control-plane:NoSchedule(구버전 master)로, 이건 자동 toleration 대상이 아닙니다.
2Node Affinity — required vs preferred▾

파드가 노드 라벨을 보고 스스로 고르는 조건입니다. taint와 달리 라벨만 봅니다.

spec:
  affinity:
    nodeAffinity:
      # 하드 조건: 맞는 노드가 없으면 Pending
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:                     # term 여러 개 = OR
        - matchExpressions:                    # 한 term 안 = AND
          - key: topology.kubernetes.io/zone
            operator: In
            values: [ap-northeast-2a]
      # 소프트 조건: 점수로 반영, 없으면 아무 노드나
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 80                             # 1~100
        preference:
          matchExpressions:
          - key: node.kubernetes.io/instance-type
            operator: In
            values: [m5.large]

연산자

operator의미
In / NotInvalues 중 하나에 포함 / 포함되지 않음(키가 없어도 NotIn은 참)
Exists / DoesNotExist키가 있음 / 없음 (values 생략)
Gt / Lt정수 비교. values에 정수 1개

nodeSelector · IgnoredDuringExecution

  • nodeSelector는 key: value 동등 비교만, 여러 개는 AND. 소프트 조건·연산자가 필요하면 nodeAffinity입니다.
  • IgnoredDuringExecution — 스케줄링 시점에만 평가합니다. 이미 Running인 파드는 노드 라벨을 지워도 축출되지 않습니다. 그래서 "라벨을 지웠는데 파드가 계속 그 노드에 있다"는 정상 동작입니다.
  • 노드 이름으로 고정하려면 matchFields: [{key: metadata.name, operator: In, values: [node1]}] — 시험에서 노드 고정 문제에 자주 씁니다.
kubectl label node node1 disktype=ssd
kubectl get nodes -l disktype=ssd
kubectl describe pod web-0 | sed -n '/Events/,$p'   # FailedScheduling 사유 확인
3Pod Affinity / Anti-Affinity — topologyKey▾

다른 파드와 같은 곳/다른 곳에 두고 싶을 때 씁니다. 기준이 되는 범위는 topologyKey가 결정합니다 — kubernetes.io/hostname이면 같은 노드, topology.kubernetes.io/zone이면 같은 존입니다.

  affinity:
    podAffinity:                            # 캐시 옆에 두고 싶다
      requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels: {app: cache}
        topologyKey: kubernetes.io/hostname
    podAntiAffinity:                        # 웹은 노드마다 하나씩 흩어 놓고 싶다
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        podAffinityTerm:
          labelSelector:
            matchLabels: {app: web}
          topologyKey: kubernetes.io/hostname
  • required anti-affinity + hostname에서 레플리카 수 > 노드 수면 초과분은 Pending입니다.
  • 대상 파드의 네임스페이스는 namespaces·namespaceSelector로 지정합니다. 둘 다 없으면 정책과 같은 네임스페이스만 봅니다.
  • 인터파드 affinity는 규모가 큰 클러스터에서 스케줄링이 눈에 띄게 느려집니다(노드마다 파드 라벨을 훑음). 가능하면 preferred나 nodeAffinity로 대체하세요.
4Static Pod — kubelet이 직접 만드는 파드▾

API 서버를 거치지 않고 각 노드의 kubelet이 매니페스트 파일을 감시해 직접 만듭니다. kubeadm 클러스터의 kube-apiserver·kube-controller-manager·kube-scheduler·etcd가 모두 static pod입니다.

# 기본 경로 (kubeadm) — 디렉터리의 .yaml/.yml 을 감시
ls /etc/kubernetes/manifests

# 경로 확인: kubelet 설정 파일 또는 실행 인자
grep -i staticPodPath /var/lib/kubelet/config.yaml
ps -ef | grep '[k]ubelet' | tr ' ' '\n' | grep -i manifest

API에서는 mirror pod로 보인다

  • 이름이 <파드이름>-<노드이름> (예: kube-apiserver-cp1), owner가 Node, annotation kubernetes.io/config.mirror.
  • 읽기 전용입니다. kubectl delete/edit 해도 kubelet이 파일을 보고 다시 만듭니다. 지우려면 노드에서 파일을 삭제해야 합니다.
  • 파일을 넣거나 지우면 수 초 안에 반영됩니다. kubelet 재시작이 필요 없습니다.
  • API 서버에 붙지 못하는 상황에서도 뜨기 때문에 컨트롤 플레인의 복구 수단이 되지만, 대신 ServiceAccount·ConfigMap·Secret 같은 API 오브젝트를 참조할 수 없습니다.
# 파드는 돌고 있는데 API에 안 보일 때
kubectl get pods -n kube-system -o wide | grep cp1
sudo crictl ps | grep kube-apiserver        # 노드 런타임에서 직접 확인
sudo journalctl -u kubelet -n 100 | grep -i -E 'static|manifest|parse'
함정 — kubectl delete pod kube-scheduler-cp1 -n kube-system 은 "삭제 성공"으로 보이지만 곧 같은 파드가 다시 나타납니다. static pod를 없애는 유일한 방법은 노드의 매니페스트 파일 삭제입니다.
5DaemonSet — 노드마다 1개 + Static Pod와의 차이▾

노드마다(또는 nodeSelector/affinity로 고른 노드마다) 파드 1개를 유지합니다. 노드가 추가되면 자동으로 하나 더 생기고, replicas 필드는 없습니다. kube-proxy·CNI·로그·모니터링 에이전트가 전형적인 용도입니다.

항목Static PodDaemonSet
관리 주체각 노드의 kubelet컨트롤러(+스케줄러)
정의 위치노드 로컬 파일API(etcd)의 오브젝트
API 노출mirror pod (읽기 전용)일반 파드
삭제파일 삭제 (kubectl delete는 되살아남)kubectl delete 가능
업데이트파일 수정 (kubelet이 반영)updateStrategy 롤링
API 오브젝트 참조불가 (SA·ConfigMap·Secret)가능

롤링 업데이트

  updateStrategy:
    type: RollingUpdate          # 기본값. OnDelete 는 수동
    rollingUpdate:
      maxUnavailable: 1

kubectl get ds -n kube-system -o wide      # DESIRED CURRENT READY UP-TO-DATE AVAILABLE
kubectl rollout status ds/kube-proxy -n kube-system
kubectl rollout restart ds/kube-proxy -n kube-system
kubectl rollout undo ds/kube-proxy -n kube-system
  • DaemonSet 컨트롤러는 not-ready·unreachable·memory-pressure·disk-pressure·pid-pressure·unschedulable toleration을 자동으로 붙입니다. 컨트롤 플레인 taint는 직접 넣어야 합니다.
  • kubectl create daemonset은 없습니다(deployment/statefulset처럼 명령형 생성 불가). YAML로 만들고 kubectl apply.
  • 파드가 안 뜨는 노드는 kubectl describe node의 Taints, kubectl get ds -o yaml의 nodeSelector/affinity를 함께 봅니다.

시험 함정 체크리스트

  • toleration은 허가일 뿐 — taint된 노드로 보내려면 nodeSelector/nodeAffinity도 필요
  • effect가 다르면 toleration은 매칭되지 않는다(NoSchedule vs NoExecute)
  • key 없이 operator: Exists = 모든 taint 견딤 / effect 생략 = 그 key의 모든 effect
  • required는 Pending, preferred는 아무 데나 — IgnoredDuringExecution은 실행 중 라벨 변경을 무시
  • nodeAffinity는 라벨, taint는 스케줄링 게이트 — 증상이 비슷해도 고치는 곳이 다름
  • DaemonSet에는 replicas가 없다, 컨트롤 플레인에는 toleration을 직접 추가
  • static pod는 파일이 곧 정의 — kubectl로 지워도 되살아남
