1StorageClass 바인딩 — Immediate vs WaitForFirstConsumer▾

동적 프로비저닝은 세 주체가 역할을 나눕니다: PVC(“이만큼, 이 모드로 주세요”라는 요청), StorageClass(어떤 프로비저너가 어떤 파라미터로 만들지), external-provisioner(실제로 PV 를 만드는 CSI 사이드카). 바인딩이 언제 일어나는지만 바꾸는 필드가 volumeBindingMode 이고, 이 한 줄이 멀티존 클러스터의 성패를 가릅니다.

바인딩 4단계

  1. PVC 는 Pending, 이벤트에 waiting for first consumer to be created before binding 이 남습니다.
  2. 스케줄러가 그 PVC 를 쓰는 파드를 놓을 노드를 고릅니다 — 자원·taint·affinity·기존 PV 의 nodeAffinity 를 모두 고려합니다.
  3. PVC 에 volume.kubernetes.io/selected-node: worker-2 어노테이션을 붙이고, 프로비저너가 그 노드의 존에 PV 를 만듭니다(PV 에 nodeAffinity 가 따라붙습니다).
  4. 컨트롤러가 바인딩을 마치고 파드가 그 노드에 스케줄됩니다. 바인딩 전에 파드가 지워지면 어노테이션도 지워지고 처음부터 다시 시작합니다.
Immediate 의 함정 — 파드가 아직 없으니 존을 데이터가 아니라 편의로 고릅니다. 그래서 파드의 nodeSelector·affinity 가 다른 존을 가리키면 볼륨은 있는데 파드가 못 뜨는 상태가 됩니다. 반대로 WFFC 에서는 파드가 Pending 이면 PVC 도 Pending 이므로, describe pod 의 FailedScheduling 메시지를 먼저 봐야 원인이 보입니다.

바꿀 수 없는 필드

  • volumeBindingMode 는 StorageClass 필드이고 생성 후 변경 불가입니다. PVC 에는 이 필드가 아예 없습니다.
  • 바꿔야 한다면 같은 프로비저너·파라미터로 새 StorageClass 를 만들고, 새 PVC 를 만든 뒤(데이터가 있으면 스냅샷/클론 복사) 파드를 새 PVC 로 옮깁니다.
  • allowedTopologies 로 생성 가능한 존을 제한할 수 있고, CSI 프로비저너의 --strict-topology 플래그는 같은 존 안에서도 선택된 노드의 토폴로지로만 만들도록 좁힙니다.

2PVC 온라인 확장 — 두 단계와 조건(Condition) 읽기▾

확장은 kubectl patch pvc 한 줄로 요청하고, 실제 처리는 두 단계로 나뉩니다. 이 두 단계를 구분하지 못하면 “용량을 늘렸는데 CAPACITY 가 그대로”에서 막힙니다.

ResizePending 조건, 파드가 볼륨을 마운트할 때 수행

그래서 kubectl describe pvc 에 FileSystemResizePending: True 가 떠 있고 파드 안 df -h 가 그대로라면, 실패가 아니라 2단계 대기입니다. 파드를 재시작(재마운트)하면 kubelet 이 파일시스템 확장을 수행합니다. Resizing 이 오래 True 로 남으면 그건 1단계, 즉 드라이버·프로비저너 쪽 문제입니다.

  • 전제: StorageClass 에 allowVolumeExpansion: true. 없으면 patch 는 되지만 컨트롤러가 “확장 미지원” 이벤트만 남깁니다.
  • 줄이는 것은 불가 — API 가 must be greater than or equal to previous value 로 거부합니다. 축소는 스냅샷 → 더 작은 새 PVC 로 복원하는 방식뿐입니다.
  • RWO 볼륨은 붙어 있는 노드에서만 파일시스템 확장이 가능합니다. 파드가 다른 노드로 옮겨 간 직후라면 재마운트가 한 번 더 필요합니다.
  • 파드가 아예 없는 PVC 는 1단계까지만 진행되고 FileSystemResizePending 으로 남습니다. 다음에 마운트될 때 정리됩니다.
  • spec.resources.requests.storage(요청)와 status.capacity.storage(실제)는 다른 값입니다. status 는 직접 patch 하는 필드가 아닙니다.
# 1) 확장 허용 여부
kubectl get sc fast -o jsonpath='{.allowVolumeExpansion}'      # true

# 2) 증설 (edit 로 해도 같다)
kubectl patch pvc data-web-0 -n prod --type=merge \
  -p '{"spec":{"resources":{"requests":{"storage":"50Gi"}}}}'

# 3) 상태: 요청값 · 실제 용량 · 조건
kubectl get pvc data-web-0 -n prod
# NAME        STATUS   VOLUME    CAPACITY   ACCESS MODES   STORAGECLASS
# data-web-0  Bound    pvc-9f2c  20Gi       RWO            fast

kubectl describe pvc data-web-0 -n prod | sed -n '/Conditions:/,/Events:/p'
# Conditions:
#   Type                      Status  Message
#   FileSystemResizePending   True    Waiting for node to expand the volume.

# 4) 파드 안 파일시스템
kubectl exec -n prod data-web-0 -- df -h /data

# 5) 재마운트로 2단계 수행
kubectl rollout restart statefulset/web -n prod     # 또는 kubectl delete pod data-web-0
kubectl get pvc data-web-0 -n prod                  # CAPACITY 50Gi, 조건 사라짐
kubectl exec -n prod data-web-0 -- df -h /data

# 여러 PVC 한꺼번에
for p in $(kubectl get pvc -n prod -o name | grep data-web); do
  kubectl patch $p -n prod --type=merge -p '{"spec":{"resources":{"requests":{"storage":"50Gi"}}}}'
done

4StatefulSet volumeClaimTemplates & 로컬 스토리지▾

volumeClaimTemplates 는 PVC 를 찍어 내는 틀입니다. 실제 PVC 이름은 <템플릿 이름>-<StatefulSet 이름>-<ordinal> — data-web-0, data-web-1 처럼 ordinal 에 묶입니다. 이 이름 규칙 덕분에 파드가 재생성되어도 같은 PVC 에 다시 붙습니다.

상황기본 동작
scale downPVC 는 남는다(Retain). 다시 scale up 하면 기존 PVC 에 붙는다
StatefulSet 삭제PVC 는 남는다. orphan 된 채로 남아 스토리지 비용이 계속된다
파드 삭제·재스케줄같은 ordinal 은 같은 PVC 에 다시 붙는다(데이터 유지)
자동 삭제spec.persistent
VolumeClaim

템플릿 수정불가(immutable) — 크기 변경은 PVC 를 개별 patch, 템플릿 변경은 StatefulSet 재생성

kubectl apply -f web-sts.yaml

local PV — 노드에 붙박이인 볼륨

apiVersion: v1
kind: PersistentVolume
metadata: { name: pv-local-ssd0 }
spec:
  capacity: { storage: 200Gi }
  accessModes: [ReadWriteOnce]
  persistentVolumeReclaimPolicy: Retain
  storageClassName: local-ssd
  local:
    path: /mnt/disks/ssd0
  nodeAffinity:                    # 필수 — 없으면 생성 거부
    required:
      nodeSelectorTerms:
      - matchExpressions:
        - key: kubernetes.io/hostname
          operator: In
          values: [worker-1]
---
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata: { name: local-ssd }
provisioner: kubernetes.io/no-provisioner
volumeBindingMode: WaitForFirstConsumer   # local PV 는 반드시 WFFC
  • nodeAffinity 는 필수입니다. 이 PV 가 어느 노드의 디스크인지 스케줄러가 알아야 파드를 그 노드에 놓습니다.
  • local PV 는 정적 프로비저닝만 가능하고 no-provisioner 클래스를 씁니다. Immediate 면 PVC 가 노드와 무관하게 먼저 묶여 파드가 못 뜰 수 있어 WFFC 가 전제입니다.
  • ReclaimPolicy: Retain 을 권합니다 — 노드 디스크의 데이터를 자동 삭제하는 것은 위험합니다.
