1Node NotReady — 위에서부터 아래로 내려가는 순서▾

노드가 NotReady 면 그 노드의 파드는 모두 원인과 무관하게 흔들립니다. 그래서 파드부터 보면 안 되고 컨트롤 플레인 → 노드 → kubelet → 런타임 → CNI 순으로 좁힙니다. kubectl get nodes가 노드 목록을 보여 준다는 것 자체가 apiserver와 etcd가 살아 있다는 증거입니다.

# 1) 컨트롤 플레인은 정상인가 (노드 목록이 보이면 이미 정상)
kubectl get nodes -o wide
kubectl -n kube-system get pod -o wide | grep -E 'apiserver|etcd|scheduler'

# 2) 노드의 Conditions · Taints · Allocated 를 한 번에
kubectl describe node worker-2 | sed -n '1,40p'
kubectl get node worker-2 -o jsonpath='{range .status.conditions[*]}{.type}={.status} {.reason} {.message}{"\n"}{end}'

# 3) 노드에 SSH 로 들어가 kubelet 부터
systemctl status kubelet
journalctl -u kubelet -xe --no-pager | tail -60
systemctl status containerd        # 런타임 (cri-dockerd 면 그 서비스)
crictl ps -a                       # 런타임이 파드를 알고 있나
crictl info | head -20

# 4) 설정 · CNI · 디스크 · swap
cat /var/lib/kubelet/config.yaml   # clusterDNS, staticPodPath, cgroupDriver
ls /etc/cni/net.d                  # 비어 있으면 CNI 미설치 → NetworkUnavailable
df -h /var/lib/kubelet /var/lib/containerd /var/lib/docker
free -h; swapon --show             # swap 이 켜져 있으면 kubelet 기동 거부
describe node / journalctl 단서의미와 조치
KubeletNotReady
container runtime is down		런타임(containerd)이 죽었거나 소켓 응답 없음 — systemctl restart containerd 후 kubelet 재시작
PLEG is not healthy런타임이 멈춰(kernel hang·디스크 I/O) kubelet 이 파드 상태를 못 읽음 — 런타임/노드 리소스 점검
failed to get node ip
network plugin is not ready		CNI 미설치·설정 없음 — CNI 파드(DaemonSet) 상태와 /etc/cni/net.d 확인
DiskPressure · MemoryPressurekubelet 이 축출(eviction)을 시작해 파드가 밀려남 — df -h, 사용하지 않는 이미지 crictl rmi --prune
NetworkUnavailableCNI 라우팅 미구성 — Ready 는 True 인데 IP 통신이 안 됨
x509: certificate has expiredkubelet 클라이언트 인증서 만료(/var/lib/kubelet/pki) — kubeadm kubelet.conf 재발급 또는 CSR 자동 회전 확인
failed to run Kubelet: misconfiguration: kubelet cgroup driver런타임(systemd)과 kubelet(cgroupfs) 불일치 — config.yaml 의 cgroupDriver: systemd 로 맞추고 재시작
taint 는 원인이 아니라 결과 — NotReady 노드에는 kubelet 이 node.kubernetes.io/not-ready:NoSchedule taint 를 자동으로 붙입니다. 이 taint 를 지워도 kubelet 이 죽어 있으면 다시 붙습니다. Ready=False 의 reason/message 를 먼저 읽고 그 아래 계층으로 내려가야 합니다.
2Pod Pending — 스케줄러가 놓지 못한 이유 5가지▾

Pending 은 노드에 배정되지 못한 상태입니다. 컨테이너는 아직 만들어지지도 않았으므로 kubectl logs 는 비어 있고, 답은 스케줄러 이벤트에 있습니다. kubectl describe pod 의 맨 아래 Events 또는 FailedScheduling 메시지가 원인을 그대로 알려 줍니다.

kubectl describe pod api-0 | tail -n 12
# Events:
#   Warning  FailedScheduling  default-scheduler
#   0/3 nodes are available: 1 node(s) had untolerated taint {dedicated: gpu},
#   2 Insufficient memory.

kubectl get events --sort-by='.lastTimestamp' -A | tail -20
kubectl get pod api-0 -o wide            # NODE 가 <none> 이면 스케줄 실패
이벤트 문구원인 · 조치
Insufficient cpu
Insufficient memory		requests 합계가 노드 Allocatable 을 넘음 — kubectl describe node 의 Allocated resources 확인 후 requests 하향 또는 노드 추가
untolerated taint노드 taint 에 맞는 tolerations 추가 (control-plane 노드에 올릴 때 단골)
didn't match Pod's node affinity/selectornodeSelector·affinity 라벨 불일치 — kubectl get nodes --show-labels
pod has unbound immediate PVCPVC 가 Pending — kubectl get pvc. WaitForFirstConsumer StorageClass 는 스케줄 시점에 바인딩되는 게 정상
node(s) didn't have free ports
exceed max volume count		hostPort 충돌, 노드당 볼륨 수 한도 — 포트/노드 분산
함정 — nodeName 직접 지정 은 스케줄러를 건너뛰는 것이지 자원 검사를 대신 받아 주는 것이 아닙니다. 자리가 없는 노드에 지정하면 kubelet 이 admit 했다가 OOM·축출·NotReady 로 끝나고, "왜 Pending 이 안 되지?" 하며 시간을 버립니다. 시험에서는 requests 를 줄이거나 toleration 추가가 정답입니다.

Pending 과 ContainerCreating 은 다릅니다. Pending = 노드 미배정(스케줄러), ContainerCreating = 노드는 정해졌는데 런타임이 못 만듦(이미지 pull·볼륨 mount·CNI IP 할당). 후자는 kubectl describe pod 의 FailedMount·FailedCreatePodSandBox 이벤트를 봅니다.

3CrashLoopBackOff — "왜 죽었나"는 lastState 에 있다▾

CrashLoopBackOff 는 원인 이름이 아니라 kubelet 의 재시작 백오프(10s→20s→40s … 최대 5분) 상태입니다. 원인은 describe pod 의 Last State: Terminated — Reason 과 Exit Code 입니다. 로그보다 이 두 줄을 먼저 봅니다.

kubectl get pod api-7d9f8c4
# NAME          READY   STATUS             RESTARTS      AGE
# api-7d9f8c4   0/1     CrashLoopBackOff   7 (42s ago)   9m

kubectl describe pod api-7d9f8c4 | sed -n '/Containers:/,/Events:/p' | tail -22
#     Last State:  Terminated
#       Reason:    OOMKilled
#       Exit Code: 137
#     Limits:   memory: 128Mi
#     Requests: memory: 64Mi

# 재시작 전 컨테이너의 로그 (--previous 가 핵심)
kubectl logs api-7d9f8c4 --previous --tail=80
kubectl logs api-7d9f8c4 -c api --previous      # 멀티 컨테이너는 -c 지정

# 상태만 기계적으로 뽑기
kubectl get pod api-7d9f8c4 -o jsonpath='{range .status.containerStatuses[*]}{.name} {.lastState.terminated.reason} {.lastState.terminated.exitCode}{"\n"}{end}'
Exit의미전형적 원인 · 조치
1앱이 스스로 종료(오류)설정·DB 접속·환경변수 누락 — --previous 로그의 마지막 스택트레이스
126 / 127실행 권한 없음 / command 없음command·args 오타, 이미지에 셸·바이너리 없음(which)
137SIGKILLOOMKilled(메모리 limit 초과) 또는 liveness 실패로 인한 강제 종료
143SIGTERM정상 종료 신호 — probe·eviction·kubectl delete 흐름

OOMKilled 은 limits.memory 를 넘어서 커널이 죽인 것입니다. 그래서 requests 를 올려도 OOM 은 그대로 나고 스케줄링만 바뀝니다. limit 을 실제 사용량에 맞춰 올리거나 앱 메모리를 줄여야 합니다. --previous 로그가 비어 있는 경우가 많은데, OOM 직전 stdout 버퍼가 남지 않기 때문이므로 로그가 없다고 "시작 전 실패"로 단정하면 안 됩니다.

probe 가 죽이는 패턴

# Liveness 가 기동보다 짧으면 → 기동 중에 죽이고 다시 시작 (무한 반복)
Liveness: http-get http://:8080/healthz delay=5s period=10s #failure=3
Events:    Warning Unhealthy  Liveness probe failed: HTTP probe failed with statuscode: 503

# 해결: startupProbe 로 기동 시간을 따로 유예 (성공 전까지 liveness/readiness 는 멈춘다)
startupProbe:
  httpGet: { path: /healthz, port: 8080 }
  periodSeconds: 5
  failureThreshold: 30        # 최대 150초까지 기다려 줌
livenessProbe:
  httpGet: { path: /healthz, port: 8080 }
  periodSeconds: 10
  failureThreshold: 3
  • liveness·startup 실패만 컨테이너를 재시작시킵니다. readiness 실패는 재시작이 아니라 Service endpoints 에서 빼는 것뿐 — 재시작이 반복되면 readiness 를 의심할 게 아니라 liveness/startup 을 봅니다.
  • failureThreshold 를 크게 늘리는 것은 죽는 시간을 늦출 뿐입니다. 기동이 느린 게 원인이면 startupProbe, 응답이 느린 게 원인이면 앱·리소스 문제입니다.
  • CreateContainerConfigError 는 CrashLoop 이전 단계입니다 — 참조한 Secret/ConfigMap 의 키 이름이 없을 때(kubectl describe 의 Error: secret "db-secret" not found).
4ImagePullBackOff · ErrImagePull — 4가지로 갈린다▾

ErrImagePull 은 pull 시도가 실패한 순간, ImagePullBackOff 는 같은 실패를 백오프로 미루는 상태입니다. 둘 다 이미지를 못 받은 것이고 원인은 이벤트 문구로 갈립니다.

kubectl describe pod api-6b9d | tail -n 8
# Events:
#   Warning  Failed  kubelet  Failed to pull image "registry.example.com/team/api:v2":
#   rpc error: code = Unknown desc = failed to pull and unpack image:
#   unexpected status code 401 Unauthorized

# 이벤트 문구로 원인 분리
kubectl get events --field-selector involvedObject.name=api-6b9d --sort-by='.lastTimestamp'
이벤트 문구원인 · 조치
manifest unknown
not found · pull access denied		태그·저장소 이름 오타, 삭제된 태그 — docker manifest inspect 로 존재 확인
401 Unauthorized
authentication required		프라이빗 레지스트리 인증 실패 — imagePullSecrets 없음/만료, SA 에 안 붙음
dial tcp … i/o timeout
no such host		노드의 네트워크·DNS·프록시 문제 — 다른 파드도 같은 증상인지 확인
toomanyrequestsDocker Hub rate limit — 인증된 pull 또는 미러 레지스트리
# Secret 생성 → 파드/Deployment 에 지정
kubectl create secret docker-registry regcred -n app \
  --docker-server=registry.example.com \
  --docker-username=robot --docker-password='***'

kubectl patch deploy api -n app -p \
  '{"spec":{"template":{"spec":{"imagePullSecrets":[{"name":"regcred"}]}}}}'

# SA 에 붙이면 그 SA 를 쓰는 모든 파드에 적용 (Deployment 마다 반복하지 않아도 됨)
kubectl patch sa app-sa -n app -p '{"imagePullSecrets":[{"name":"regcred"}]}'

# 노드 단위 문제인지 분리: 자격증명 없이 노드에서 직접 pull
crictl pull registry.example.com/team/api:v2
crictl images | grep team/api

imagePullPolicy 기본값은 태그가 latest(또는 생략)면 Always, 고정 태그면 IfNotPresent 입니다. 태그를 고정했는데 예전 이미지가 계속 뜨면 Always 로 바꾸거나 파드를 재생성합니다. crictl pull 이 노드에서 성공하면 파드 spec(secret·SA) 문제, 실패하면 노드 네트워크/자격증명 문제입니다.

5실전 진단 도구 · 시험 함정 체크리스트▾ 
# 1) 이벤트를 시간순으로 — 1시간만 보관되므로 가장 먼저
kubectl get events -A --sort-by='.lastTimestamp' | tail -30
kubectl get events -n app --field-selector involvedObject.kind=Pod

# 2) 리소스 실사용 (metrics-server 필요)
kubectl top node
kubectl top pod -n app --sort-by=memory --containers

# 3) 노드 레벨 디버깅 (호스트 파일시스템·네트워크를 그대로 보는 파드)
kubectl debug node/worker-2 -it --image=busybox -- chroot /host
kubectl debug -it api-7d9f8c4 --image=busybox --target=api   # distroless 앱에 셸 붙이기

# 4) 런타임 레벨 (노드에서)
crictl pods; crictl ps -a; crictl logs <container-id>; crictl inspect <id> | head -40

# 5) 한 번에 상태 훑기
kubectl get pod -A -o wide | grep -vE 'Running|Completed'
kubectl get node,pod -A -o wide | grep -E 'NotReady|Pending|Error|BackOff'
증상1차 확인원인 계층
NotReadydescribe node Conditions → SSH systemctl status kubeletkubelet · 런타임 · CNI · 디스크
Pendingdescribe pod 의 FailedScheduling스케줄러(requests·taint·selector·PVC)
ContainerCreatingFailedMount · FailedCreatePodSandBox볼륨 · CNI · 이미지 pull
ImagePullBackOffFailed to pull image 문구레지스트리 인증 · 태그 · 노드 네트워크
CrashLoopBackOfflastState Reason/Exit + logs --previous앱 오류 · OOM · probe
Running 인데 응답 없음readiness 상태 · Service endpointsreadiness · Service selector · NetworkPolicy

시험 함정 체크리스트

  • kubectl get nodes 가 되면 컨트롤 플레인은 정상 — 노드 계층부터 본다
  • NotReady 노드의 not-ready taint 는 결과 — 지워도 다시 붙는다
  • Pending = 스케줄러(이벤트), ContainerCreating = 런타임(mount·CNI·pull)
  • 스케줄링 기준은 requests, OOM 기준은 limits
  • nodeName 직접 지정은 스케줄러만 건너뛸 뿐 자원 한도를 넘겨 주지 않는다
  • 재시작을 일으키는 건 liveness·startup, readiness 는 트래픽에서만 제외
  • --previous 로그가 비었다고 실패 원인을 단정하지 않는다 — lastState 가 근거
  • ErrImagePull → ImagePullBackOff 는 같은 실패의 두 단계
  • 이벤트는 1시간만 남는다 — 재현 직후에 읽어야 한다
